This section includes information on managing your {PRODUCT_SHORT} licenses for containerized and non-containerized deployments of {PRODUCT_SHORT} components and _Business Services_.

== {PRODUCT_SHORT} component containers with IBM License Service (ILS)
Follow the https://www.ibm.com/docs/en/cloud-paks/foundational-services/4.x_cd?topic=license-service[procedure to install IBM License Service] for stand-alone software.

NOTE: The link directs you to the instructions on installing the standalone version of IBM License Service included in the IBM Cloud Pak(TM) Foundational Services. It is important to note that the {PRODUCT_SHORT} is not part of IBM Cloud Pak(TM).

When you install a component via the product specific Dev and Runtime Helm charts that correspond to your IBM license ({PRODUCT_DM} or {PRODUCT_PAM}), preconfigured license annotations are included in the global values. These annotations are automatically propagated to all sub-chart deployments and merged with any custom pod annotations. 

The merge uses the Helm merge function and happens in each deployment template. The `chargedProductAnnotations` (containing License Manager metadata) are combined with `podAnnotations` (any custom annotations). The template expressions are evaluated using the `tpl` function, which replaces token references with actual values from the global configuration.

If you choose not to install via these Helm charts, the license tracking annotations must be manually added to the container deployment YAML or to each of the {PRODUCT_SHORT} containers after installation. 

For {PRODUCT_DM}:

[source,yaml,subs="attributes+"]
----
spec:
  template:
    metadata:
      annotations:
        productID: "46b14c7f2f894218a7879b3f6416024f"
        productName: "IBM Decision Manager Open Edition"
        productMetric: "VIRTUAL_PROCESSOR_CORE"
        productChartedContainers: "All"
        includeSWCUpload: true
----


Or the following for {PRODUCT_PAM}:

[source,yaml,subs="attributes+"]
----
spec:
  template:
    metadata:
      annotations:
        productID: "72984f114b54496a8a44be139154a988"
        productName: "IBM Process Automation Manager Open Edition"
        productMetric: "VIRTUAL_PROCESSOR_CORE"
        productChargedContainers:"All"
        includeSWCUpload: true

----

Where `includeSWCUpload` indicates whether the Virtual Processor Core count is uploaded to Software Central automatically or manually (see xref:reporting-usage-metrics.adoc[Collecting and sending metrics to IBM Software Central])

----
  
* Kubernetes - {PRODUCT_DM}

== Containerized Business Services deployment using IBM License Service (ILS)
Follow the https://www.ibm.com/docs/en/cloud-paks/foundational-services/4.x_cd?topic=license-service[procedure to install IBM License Service] for stand-alone software.

You can then use ILS to track licenses in your Business Services deployed as containers in a Kubernetes or OpenShift environment. To activate this you must define license tracking annotations in a version-controlled deployment YAML file in the pod template metadata, under `spec.template.metadata.annotations`:

For {PRODUCT_DM}:

[source,yaml,subs="attributes+"]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-business-service
spec:
  template:
    metadata:
      annotations:
        productName: "IBM Decision Manager Open Edition"
        productID: "46b14c7f2f894218a7879b3f6416024f"
        productVersion: "{VERSION}"
        productMetric: "VIRTUAL_PROCESSOR_CORE"
        includeSWCUpload: true
----

Or the following for {PRODUCT_PAM}:

[source,yaml,subs="attributes+"]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-business-service
spec:
  template:
    metadata:
      annotations:
        productName: "IBM Process Automation Manager Open Edition"
        productID: "72984f114b54496a8a44be139154a988"
        productVersion: "{VERSION}"
        productMetric: "VIRTUAL_PROCESSOR_CORE"
        includeSWCUpload: true
----

Where `includeSWCUpload` indicates whether the Virtual Processor Core count is uploaded to Software Central automatically or manually (see xref:reporting-usage-metrics.adoc[Collecting and sending metrics to IBM Software Central])

=== Patching previously deployed _Business Services_ containers
If you have _Business Services_ that are deployed in a production environment you can add the required annotations using kubectl patch, in the following way:

[source,bash]
----
kubectl patch deployment <deployment-name> -p '
spec:
  template:
    metadata:
      annotations:
        productName: "<product-name>"
        productID: "<product-id>"
        productVersion: "9.5.0"
        productMetric: "VIRTUAL_PROCESSOR_CORE"
----

=== Validating annotations
Once you have included required annotations either before deployment or by patching, you can verify that all is correct using the following command:

[source, bash]
----
kubectl get deployment <name> -o yaml
----

The following example shows a command to verify and filter the "annotations" part of the YAML file:

[source, bash]
----
kubectl get deployment <deployment-name> -n <namespace> -o yaml | grep -A 5 "annotations:"
----

And will result in the following type of output:

[source, yaml]
----
annotations:
  productName: "<product-name>"
  productID: "<product-id>"
  productVersion: "9.5.0"
  productMetric: "VIRTUAL_PROCESSOR_CORE"
----

=== Enforcing licensing policy
If you want to enforce license tracking annotations in all deployments, ensure they are not removed or modified by an unauthorized person and maintain an audit trail, you can implement external policy enforcement in one of the following ways: 

* Using Kyverno (Kubernetes-native) which works across all Kubernetes distributions including OpenShift, validates deployments at cluster level and rejects deployments that don't have required annotations. 
* Using the native OpenShift capability: OpenShift Admission Policies (available in OpenShift 4.17+), integrated with OpenShift admission control system. 

. Install Kyverno on Kubernetes/OpenShift cluster.
. Create namespace naming convention to isolate BAMOE deployments into dedicated namespaces (e.g., `bamoe-production`, `bamoe-dev`)
. Choose a scoping strategy:
** Label-based (Opt-in): Label specific namespaces with `audit-scope: "true"`
** Pattern-based (Automatic): Use wildcard patterns to match namespaces (e.g., `bamoe-*`)
** Exclude system namespaces to prevent disruption (`kube-system`, `kube-public`, `openshift-*`, etc.)
. Define Kyverno policy to validate required annotations in `spec.template.metadata.annotations`
. Test policy in audit mode in non-production environments
. Switch to enforce mode after validation
. Monitor policy reports

The following example shows pattern-based namespace scoping:

[source,yaml]
----
match:
  any:
    - resources:
        namespaces:
          - "bamoe-*"  # Automatically applies to bamoe-production, bamoe-dev, etc.
----

The following example shows how to verify policy enforcement using Kyverno:

[source,bash]
----
kubectl get clusterpolicy -A
kubectl describe clusterpolicy <policy-name>
----

== Non-containerized Business Services deployment using IBM License Metric Tool (ILMT) 
IBM® License Metric Tool generates reports to help you maintain compliance with your Virtual Processor Core (VPC) license terms. It calculates VPC consumption when software identification tags exist and are activated by the customer. 

See the section, https://www.ibm.com/support/pages/downloading-ibm-license-metric-tool-92[License Metric Tool with disconnected scanners to install on Linux or Windows] on the page, for guidelines on how to obtain and install ILMT.

If you are developing traditional Java applications, non-containerized Quarkus or Spring Boot applications or using embedded mode, the following libraries must be included in your application:

|=== 
|Chargeable Software Components| Libraries

|{PRODUCT_DM}
|`com.ibm.bamoe:ilmt-compliance-quarkus-dmoe` (Quarkus) _or_
 `com.ibm.bamoe:ilmt-compliance-spring-boot-dmoe` (Spring Boot) _or_
 `com.ibm.bamoe:ilmt-compliance-java-dmoe` (Java)

|{PRODUCT_PAM} 
|`com.ibm.bamoe:ilmt-compliance-quarkus-pamoe` (Quarkus) _or_
 `com.ibm.bamoe:ilmt-compliance-spring-boot-pamoe` (Spring Boot) _or_
 `com.ibm.bamoe:ilmt-compliance-java-pamoe` (Java)
|===

If you developed your _Business Service_ using the project Accelerators the required libraries are part of your project POM and will need to be uncommented manually for non-containerized deployments (see xref:../getting-started/project-setup.adoc#gs-accelerators[Getting Started → Introducing Accelerators]). For the full Maven dependency see xref:../reference-guide/maven-repository-libraries.adoc[Reference → {PRODUCT_SHORT} Maven repository libraries]

These libraries use the system variable SWIDTAG_DIR to determine the directory for creating a swidtag file. If the SWIDTAG_DIR variable is set, the library uses the specified directory for swidtag file creation. 
If the SWIDTAG_DIR is not set, the library defaults to the home directory of the hosting application.

It is important to note that if the SWIDTAG_DIR environment variable contains invalid content or an invalid path, the hosting application fails to deploy.

The swidtag file is an XML file content based on ISO/IEC 19770-2:2015 specification. 
Following is an example of the swidtag file content:

[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<SoftwareIdentity name="IBM Decision Manager Open Edition" tagId="ibm.com-3d9d28f19d0f45fda113c07fb481e3ea-9.0.0" version="9.0.0" versionScheme="multipartnumeric" xml:lang="en" xmlns="http://standards.iso.org/iso/19770/-2/2015/schema.xsd" xmlns:ds="http://www.w3.org/2000/09/xmldsig#" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:schemaLocation="http://standards.iso.org/iso/19770/-2/2015-current/schema.xsd schema.xsd">
    <Meta persistentId="3d9d28f19d0f45fda113c07fb481e3ea"/>
    <Meta generator="4-1-20210113"/>
    <Entity name="IBM" regid="ibm.com" role="licensor tagCreator softwareCreator"/>
</SoftwareIdentity>
----
