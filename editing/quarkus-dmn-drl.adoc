You can create a _Business Service_ using the Decision and Rule engines with the Quarkus framework support.

During the compilation, some code is automatically generated by a specific Maven plugin where part of the code is common and rest of it is engine-specific.

For each model, REST endpoints are generated, that are specific to the model and the engine.

Developers can add custom classes to the _Business Service_ project to provide additional functionality, which will be built with the automatically generated code as in normal Java applications.
You can create a _Business Service_ using the Decision and Rule engines with the Quarkus framework support.

== Code structure

Beside the POM file, customize the application with Quarkus or BAMOE specific properties in the `application.properties` file. For more information about `application.properties` file, see xref:../reference-guide/application-properties.adoc[Application Properties Configuration reference].

If you want to customize logging output, provide `logback.xml` file.

_Business Service_ projects containing Decisions follow https://maven.apache.org/guides/introduction/introduction-to-the-standard-directory-layout.html[Maven's standard  directory layout].

You need to create Decisions (DMN), Rules (DRL), `application.properties` and `logback.xml` files in the `src/main/resources` directory.

If you want to change the behavior during test execution, you can also create `application.properties` and `logback.xml` files in the `src/test/resources` directory.

Your generated code is in `target/generated-sources/kogito` directory.

== Testing

For full integration tests, {PRODUCT_SHORT} provides an out-of-the-box feature to test your DMN assets by using xref:../editing/authoring-scesim.adoc[Test Scenarios].

As an alternative, you can use the JUnit framework using Java Classes that should be annotated as `@QuarkusTest`, eventually injecting required managed properties or beans.

Here is an example that verifies the response received when posting an HTTP request on a given (automatically generated) entry point for a Decision:

[source,java]
----
@QuarkusTest
public class TrafficViolationTest {


    @Test
    public void testEvaluateTrafficViolation() {
        given()
                .body("{\n" +
                        "    \"Driver\": {\n" +
                        "        \"Points\": 2\n" +
                        "    },\n" +
                        "    \"Violation\": {\n" +
                        "        \"Type\": \"speed\",\n" +
                        "        \"Actual Speed\": 120,\n" +
                        "        \"Speed Limit\": 100\n" +
                        "    }\n" +
                        "}")
                .contentType(ContentType.JSON)
                .when()
                .post("/Traffic Violation")
                .then()
                .statusCode(200)
                .body("'Should the driver be suspended?'", is("No"));
    }
}
----

It is also possible to execute tests on native image. To do so:

. Extend a testing class annotated as `@QuarkusTest`
. Annotate that new class with `@QuarkusIntegrationTest`, e.g.,

[source,java]
----
@QuarkusIntegrationTest
public class NativeTrafficViolationIT extends TrafficViolationTest {
    // Execute the same tests but in native mode.
}
----

=== Choosing Test scenarios over JUnit
The following table provides you the options to select the best choice between the Test scenarios and JUnit.

|===
| *Details* | *Test scenarios* | *JUnit*

| *Purpose*
| Behavior-Driven Development (BDD)
| Unit testing

| *Test Style*
| Human-readable scenarios using Scesim
| Code-centric test methods

| *Audience*
| Non-technical stakeholders and developers
| Primarily developers

| *Test Definition*
| .scesim files
| Java test classes and methods

| *Readability*
| High (tabular data)
| Medium (requires code understanding)

| *Tooling*
| Test scenarios
| Native to Java, integrates well with IDEs and CI tools

| *Test Granularity*
| Often higher-level and black-boxed (cannot be integrated with other tool/extensions)
| All-level (unit, method-level, integration-level)

| *Debugging*
| Not possible to debug
| Direct and easier in IDEs
|===

== Compilation

During Maven's compilation phase, `io.quarkus:quarkus-maven-plugin` scans the `src/main/resources` directory to find any `.dmn` or `.drl` files.

For each discovered file, the decision engine creates REST Resource classes, with endpoints specifically to:

. Retrieve the original model
. Execute the model
. Execute the model and retrieve “explanation” information

The classes are generated in a package whose name reflects the namespace of the DMN files, while the name of the generated class and the endpoint root are derived from the name of the model itself. For Rules, the classes are generated in the package of the DRL file.

== Execution in Dev mode

The following Maven command compile from scratch and start the Quarkus application in Dev mode:

[source,shell]
----
mvn clean compile quarkus:dev
----

After a successful start, the application will be available at `\http://:0.0.0.0:8080` address (IP depends on `application.properties` configuration).

The Swagger UI page (`\http://0.0.0.0:8080/q/swagger-ui/`) shows all the generated endpoints, providing a way to quickly verify them.

== Hot-reload in Dev mode

For medium to large sized applications, recompiling and restarting the application upon code changes could be cumbersome and time-consuming. To simplify that, the Quarkus framework offers an embedded hot-reload feature.

To fire it, there are two steps required:

. Modify any source/resource.
. Reload any page of the generated application.


== Debugging

The way to debug the application without using specific IDE tools or plug-ins, relies on the standard Java remote debug setup:

. Create a remote debug configuration on port 5005 (details vary by IDE).
. Start application in Dev mode.
+
[source,shell]
----
mvn clean compile quarkus:dev
----
+
. Put a breakpoint in some of the code-generated sources.
. Connect the remote debugger.
+
You can also block the compilation until a debugger is connected using the following command which enables you to debug code generation:
+
[source,shell]
----
mvn clean compile quarkus:dev -Dsuspend
----
