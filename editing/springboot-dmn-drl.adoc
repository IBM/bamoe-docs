= Decisions and Rules services with Spring Boot
include::../partials/attributes.adoc[]
include::../styles/images.adoc[]

You can create a _Business Service_ using the Decision and Rule engines with the Spring Boot framework support. If you developed your _Business Service_ using the project Accelerators the required libraries are part of your project POM and will need to be uncommented manually for non-containerized deployments (see xref:../getting-started/project-setup.adoc#gs-accelerators[Getting Started → Introducing Accelerators]). For the full Maven dependency see xref:../reference-guide/maven-repository-libraries.adoc[Reference → {PRODUCT_SHORT} Maven repository libraries].

During the compilation, some code is automatically generated by a specific Maven plugin where part of the code is common and the rest of it is engine-specific.

For each model, REST endpoints are generated, that are specific to the model and the engine.

Developers can add custom classes to the _Business Service_ project to provide additional functionality, which is built with the automatically generated code as in normal Java applications.

== Dependencies

Use the Spring Boot BOM to facilitate management of all {PRODUCT_SHORT} libraries.

Add the `com.ibm.bamoe:bamoe-spring-boot-bom` dependency to the `<dependencyManagement>` section of your project POM. You can then add the dependencies you require from those available in the BOM POMs using the `<dependency>` tags. For more information, see xref:../reference-guide/maven-repository-libraries.adoc#_bamoe_boms_bill_of_materials[BAMOE Bill of Materials (BOM)].

Use the `org.drools:drools-decisions-spring-boot-starter` and `org.drools:drools-rules-spring-boot-starter` dependencies that are required for a Decision or Rules application with Spring Boot. For more information, see xref:../reference-guide/maven-repository-libraries.adoc#_decisions_rules_and_decision_tables_spring_boot[Decisions, Rules, and Decision Tables (Spring Boot)].

Use `org.springframework.boot:spring-boot-starter-actuator` dependency for a workflow _Business Service_ project built with Spring Boot. For more information, see xref:../reference-guide/maven-repository-libraries.adoc#_workflows_spring_boot[Workflows (Spring Boot)].

To enable hot-reload during development, use `org.springframework.boot:spring-boot-devtools` dependency. For more information, see xref:https://central.sonatype.com/artifact/org.springframework.boot/spring-boot-devtools[`org.springframework.boot:spring-boot-devtools`] external documentation.

To enable Test Scenario support, use `org.kie.kogito:kogito-scenario-simulation` dependency. For more information, see xref:../reference-guide/maven-repository-libraries.adoc#_decisions_rules_and_decision_tables_dev_testing[Decisions, Rules, and Decision Tables (Dev + testing)].

To correctly build and package the application, use `org.kie.kogito:kogito-maven-plugin` and the `org.springframework.boot:spring-boot-maven-plugin` Maven plugins. For more information, see xref:https://central.sonatype.com/artifact/org.kie.kogito/kogito-maven-plugin[`org.kie.kogito:kogito-maven-plugin`] and xref:https://central.sonatype.com/artifact/org.springframework.boot/spring-boot-maven-plugin[`org.springframework.boot:spring-boot-maven-plugin`] external documentation.

For `org.kie.kogito:kogito-maven-plugin` dependency, see xref:../reference-guide/maven-repository-libraries.adoc#_decisions_rules_and_decision_tables_spring_boot[Decisions, Rules, and Decision Tables (Spring Boot)].

For more information on _Business Services_ with Decisions on Spring Boot, see the {BAMOE_DOCS_EXAMPLES_DOCS_LINK}/spring-boot/decisions/pom.xml[complete POM for Decisions]. 
For more information on _Business Services_ with Rules on Spring Boot, see {BAMOE_DOCS_EXAMPLES_DOCS_LINK}/spring-boot/rules/pom.xml[complete POM for Rules].

== Code structure

Besides the POM file, customize the application with Spring Boot or BAMOE specific properties in the `application.properties` file. For more information about `application.properties` file, see xref:../reference-guide/application-properties.adoc[Application Properties Configuration reference].

If you want to customize logging output, provide a `logback.xml` file.

_Business Service_ projects containing Decisions follow https://maven.apache.org/guides/introduction/introduction-to-the-standard-directory-layout.html[Maven's standard directory layout].

You need to create Decisions (DMN), Rules (DRL), `application.properties` and `logback.xml` files in the `src/main/resources` directory.

If you want to change the behavior during test execution, you can also create `application.properties` and `logback.xml` files in the `src/test/resources` directory.

Your generated code is in `target/generated-sources/kogito` directory.

For all Spring Boot applications, an entry point class annotated with `@SpringBootApplication` is required. 

For Decisions, the following entry point class annotated with `@SpringBootApplication` is required:

[source,java]
----
@SpringBootApplication(scanBasePackages = { "org.kie.kogito.dmn.**", "org.kie.kogito.app.**", "http**" })
public class KogitoSpringbootApplication {
    public static void main(String[] args) {
        SpringApplication.run(KogitoSpringbootApplication.class, args);
    }
}
----

For Rules, the following entry point class annotated with `@SpringBootApplication` is required:

[source,java]
----
@SpringBootApplication(scanBasePackages = { "org.kie.kogito.**", "org.drools.**" })
public class KogitoSpringbootApplication {
    public static void main(String[] args) {
        SpringApplication.run(KogitoSpringbootApplication.class, args);
    }
}
----

== Testing

For full integration tests, {PRODUCT_SHORT} provides an out-of-the-box feature to test your DMN assets by using xref:../editing/authoring-scesim.adoc[Test Scenarios].

As an alternative, you can use the JUnit framework using Java Classes that should be annotated as `@SpringBootTest`, optionally injecting required managed properties or beans.

Here is an example that verifies the response received when posting an HTTP request on a given (automatically generated) entry point for a Decision:

[source,java]
----
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT, classes = KogitoSpringbootApplication.class)
@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_EACH_TEST_METHOD)
public class TrafficViolationTest {

    @LocalServerPort
    private int port;

    @BeforeEach
    public void setUp() {
        RestAssured.port = port;
    }

    @Test
    public void testEvaluateTrafficViolation() {
        given()
                .body("{\n" +
                        "    \"Driver\": {\n" +
                        "        \"Points\": 2\n" +
                        "    },\n" +
                        "    \"Violation\": {\n" +
                        "        \"Type\": \"speed\",\n" +
                        "        \"Actual Speed\": 120,\n" +
                        "        \"Speed Limit\": 100\n" +
                        "    }\n" +
                        "}")
                .contentType(ContentType.JSON)
                .when()
                .post("/Traffic Violation")
                .then()
                .statusCode(200)
                .body("'Should the driver be suspended?'", is("No"));
    }
}
----

=== Choosing Test scenarios over JUnit
The following table provides you the options to select the best choice between the Test scenarios and JUnit.

|===
| *Details* | *Test scenarios* | *JUnit*

| *Purpose*
| Behavior-Driven Development (BDD)
| Unit testing

| *Test Style*
| Human-readable scenarios using Scesim
| Code-centric test methods

| *Audience*
| Non-technical stakeholders and developers
| Primarily developers

| *Test Definition*
| .scesim files
| Java test classes and methods

| *Readability*
| High (tabular data)
| Medium (requires code understanding)

| *Tooling*
| Test scenarios
| Native to Java, integrates well with IDEs and CI tools

| *Test Granularity*
| Often higher-level and black-boxed (cannot be integrated with other tool/extensions)
| All-level (unit, method-level, integration-level)

| *Debugging*
| Not possible to debug
| Direct and easier in IDEs
|===

== Compilation

During Maven’s compilation phase, `org.kie.kogito:kogito-maven-plugin` scans the `src/main/resources` directory to find any `.dmn` or `.drl` files. 

For each discovered file, the decision engine creates REST Resource classes, with endpoints specifically to:

. Retrieve the original model
. Execute the model
. Execute the model and retrieve “explanation” information

The classes are generated in a package whose name reflects the namespace of the DMN files, while the name of the generated class and the endpoint root are derived from the name of the model itself. For Rules, the classes are generated in the package of the DRL file.

== Execution in Dev mode

The following Maven command compiles from scratch and starts the Spring Boot application in Dev mode:

[source,shell]
----
mvn clean compile spring-boot:run
----

After a successful start, the application will be available at `\http://0.0.0.0:8080` address (IP depends on `application.properties` configuration).

The Swagger UI page (`\http://0.0.0.0:8080/swagger-ui/index.html`) shows all the generated endpoints, providing a way to quickly verify them.

== Hot-reload in Dev mode

For medium to large sized applications, recompiling and restarting the application upon code changes could be cumbersome and time-consuming. To simplify that, the Spring Boot framework offers https://docs.spring.io/spring-boot/3.4/reference/using/devtools.html[devtools].

The condition is that the classpath has to be "manually" rebuilt to trigger the reload. 

Since _Business Services_ also rely on automatic code-generation driven by models and executed by the 'kogito-maven-plugin', the approach is to:

. Create an `mvn clean compile` shortcut (details vary by IDE) to trigger on demand.
. Start the application with `mvn clean compile spring-boot:run`.
. Execute the command from step 1 when reloading changes is required.

== Debugging

To debug the application without specific IDE tools or plug-ins, use the standard Java remote debug setup:

. Create a remote debug configuration on port 8000 (details vary by IDE).
. Start application in debug mode.
+
[source,shell]
----
mvn clean compile spring-boot:run -Dspring-boot.run.jvmArguments="-Xdebug -Xrunjdwp:transport=dt_socket,server=y,suspend=y,address=8000"
----
+
. Put a breakpoint in one of the generated source files.
. Connect the remote debugger.
