= Exposing {PRODUCT_SHORT} capabilities to AI agents

include::../styles/images.adoc[]

The {MCP_SERVER} technology preview provides a dedicated and isolated layer that actively exposes _Business Services_, including rule evaluation, decision models, and process orchestration, through a standardized interface optimized for agentic workflows. It is provided as a Docker image to facilitate deployment in the environment it is being used in. 

== Introducing {MCP_SERVER} tech preview

You can use it to build intelligent assistants, autonomous systems, or orchestrate complex business logic. It enables agents to reason, decide, and act with precision. By default, the {MCP_SERVER} runs without authentication, but from {VERSION} you can choose to enable security by configuring a set of environment variables that connect the server to a Keycloak realm (see xref:#configure-security[Configuring MCP Server Security]).

The {MCP_SERVER} exposes the following capabilities of _Business Services_: 

* Decision model execution (DMN)
* Rule model execution
* A Process API that allows agents to create, retrieve, modify, and delete process instances.

== Preparing _Business Services_ to be exposed to {MCP_SERVER}

In order for this feature to work you will need the following four components:

* _Business Service_ that defines the REST endpoints that will be exposed through the {MCP_SERVER}.
* The deployed docker image of {MCP_SERVER}.
* If you require security, an authentication server that is shared by the _Business Service_ and the {MCP_SERVER} (default is the Keycloak server), see xref:#mcp-server-security[Configuring {PRODUCT_SHORT} security].
* An MCP Client that may interact with the {MCP_SERVER}.

The MCP Server parses information retrieved from the retrieved from the target _Business Service_  to discover and translate into _MCP Tools_. It uses the OpenAPI information exposed by the _Business Service_. 

To prepare the {PRODUCT_SHORT} capabilities to be exposed to the {MCP_SERVER}:

. Run a _Business Service_ instance using Quarkus or Spring Boot (not supported in {VERSION_930}) with the following setup.
+
* For Quarkus based Business Services, the OpenAPI v3 spec is exposed via this URI `http://<yourhost>:<port>/q/openapi` by default. which can be overridden with the property `quarkus.smallrye-openapi.path`.
+
* For Spring-boot based Business Services, the OpenAPI v3 spec is exposed in this URI `http://<yourhost>:<port>/v3/api-docs` by default. 

. Define meaningful names for models, fields, and nodes in _Business Services_ to improve the effectiveness of AI agent interactions. If there is a description in the _Business Service_ model it will be added to the MCP Tool description. 

. Configure rule models appropriately: 
//remove the RuleUnit based models? Why aren't we referring to DMN?
+
* For RuleUnit based models, annotate each implemented `DataStore<>` class with `@Schema`, specifying the implementation class.
+
For example, in case of `DataStore<Person>` the annotation should be added as:
+
[source,properties]
----
@Schema(implementation = Person.class)
private DataStore<Person> persons;
----
+
* For plain DRLs without RuleUnits, manually define and expose model endpoints, as they are not generated automatically.

. Use the `bamoe / mcp-server` image available in your container orchestration platform.

== Running and managing the {MCP_SERVER} lifecyle (no security)

To run the {MCP_SERVER}, complete the setup and launch the server image in a Docker environment using the following command:

[source,shell, subs="attributes+"]
----
docker run -it --rm \
  -p 8081:8080 \
  --name mcp-server \
  -e MCP_SERVER_OPENAPI_URLS="http://host.docker.internal:8080/q/openapi" \
  quay.io/bamoe/mcp-server:{IMAGE_VERSION}
----

At startup, the MCP Server parses all exposed {PRODUCT_SHORT} Business Services and translates their capabilities into MCP Tools. These tools become available to any MCP-compatible client or agentic AI environment that supports the MCP protocol, allowing users to seamlessly integrate {PRODUCT_SHORT} automation features into AI-driven workflows.

Once running, the MCP Server begins serving requests from AI agents. Its internal state remains immutable, so any changes to the underlying _Business Services_ are not automatically reflected. To apply updates, you must restart the MCP Server. A recommended approach is to use a reverse proxy to manage the lifecycle and handle image immutability internally.

Any MCP-compatible client that supports the MCP protocol can consume the {MCP_SERVER}, for example Goose, 5ire, LM Studio, and Claude Desktop.

The client configuration depends on the chosen MCP client, but typically the MCP Server is treated as an extension. To connect, provide the following details in the extension section of the MCP client:

Extension name:: Any meaningful name
Type:: HTTP streamable
Endpoint:: MCP Server endpoint (`http://<host>:<port>/mcp`)

Where `<port>` defaults to 80 for http or 443 for https (see xref:#mcp-server-security[Configuring Security]), if you do not specify a specific port. 

NOTE: Server-Sent Events (SSE) is supported but deprecated, and Standard IO (STDIO) is not supported.

One of the most useful aspects of the MCP Tools is their integration with AI agents, such as large language models (LLMs). These agents can dynamically invoke decision models, rule engines, and process APIs, bringing {PRODUCT_SHORT} automation capabilities directly into Agentic workflows.

== Configuring {MCP_SERVER} security

If the _Business Service_ is also secured, it is essential to integrate the security layers of both the {MCP_SERVER} and the _Business Service_. This ensures that the same access token used to authenticate with the MCP Server can be propagated and reused to securely access the _Business Service_. 

Once the Business Services endpoints and the MCP server are secured under the same security layer, sharing the same credentials, you can configure realm and credentials for the integration. This section outlines how to secure your MCP Server endpoints using an OpenID Connect (OIDC) Provider, such us as Keycloak. 

=== Setting up Keycloak

* Keycloak must be accessible at a known domain.
* Realm must be configured with:
** `client-id` and `client-secret`
** `Users` and `roles`
** Token settings (expiration, scopes, etc.).
** Other requirements specific to Keycloack (e.g. database used for persistence) are not covered here. 

=== Importing Realm Configuration
If a realm configuration already exists, it may be imported in Keycloak at startup.

The following shows an example on how to launch a Keycloak instance in a docker environment.

[source, shell]
----
docker run -d \
 --name keycloak \
 -e KEYCLOAK_ADMIN=admin \
 -e KEYCLOAK_ADMIN_PASSWORD=admin \
 -e KC_IMPORT=/opt/keycloak/data/import/realm.json \   # Path inside container where realm file is mounted
 -v /path/to/realm.json:/opt/keycloak/data/import/realm.json \  # Replace with your actual file path
 -p 8443:8443 \
 quay.io/keycloak/keycloak:26.3 \
 start --optimized --import-realm
----

The following snippet shows the same command integrated into a `docker-compose.yml` file. 

[source, xml]
----
[...]
keycloak:
    container_name: keycloak
    image: quay.io/keycloak/keycloak:26.3
    environment:
      - KC_BOOTSTRAP_ADMIN_USERNAME=admin
      - KC_BOOTSTRAP_ADMIN_PASSWORD=admin
    ports:
      - 8443:8443
    volumes:
      - /path/to/{realm_name}-realm.json:/opt/keycloak/data/import/{realm_name}-realm.json
    command: [ "optimized", "--import-realm" ]
    restart: unless-stopped
----

Where `/path/to/{realm_name}-realm.json` is replaced by your actual file path.

=== Integrating Security across {MCP_SERVER} and your _Business Services_
When both the {MCP_SERVER} and the _Business Service_ are secured, you will need to integrate their security layers, to ensure that:

* The same access token used to authenticate the user with the MCP Server can also be used to securely access the _Business Service_. 
* The MCP Server can forward the token when calling _Business Service_ endpoints, maintaining a consistent and trusted identity across services.
* Token propagation is required so that the _Business Service_ trusts requests coming from the {MCP_SERVER} on behalf of the authenticated user.

In this way users are not required to authenticate separately for each service and seamless, secure communication between components is made possible.

You must set up the following configuration to ensure secure communication between the {MCP_SERVER} and the _Business Service_.

.Shared Realm and Credentials

To ensure secure communication and consistent authentication, for Quarkus or Spring Boot Based _Business Services_, the MCP Server and the Business Service must use the same Keycloak realm and credentials:

client-id:: <your_client_id>
client-secret:: <your_client_secret>
Realm:: <your_realm_name>
Domain:: keycloack_domain

This enables both services to validate users using the same identity provider.

In the xref:../building-deploying/security.adoc[Securing Business Service API endpoint] section, you will find information on how to enable the security layer for a _Business Service_ instance. You can reuse the same parameters from that configuration to configure the MCP Server Security layer, as described in the next paragraph.

.MCP Server Image Configuration

When deploying the MCP Server using a Docker image, configure security using environment variables. By setting `MCP_SERVER_SECURITY_ENABLED=true` and `MCP_SERVER_SECURITY_AUTH_PERMISSION=authenticated`, all `/mcp/*` endpoints will be under security and require a valid Bearer token for authentication.

The token must be issued by the Keycloak realm specified in the `MCP_SERVER_SECURITY_AUTH_SERVER_URL` environment variable.

[%header,cols=3]
[%autowidth]
|===

|Environment variable | Description | Required value 
|`MCP_SERVER_SECURITY_ENABLED`
|A boolean that determines whether to enable the security layer.
|`true` (default is `false`)

|`MCP_SERVER_SECURITY_OIDC_CLIENT_ID`
|A string which defines the `client_id` for the authentication process. 
|`<your_Client_id>`, must match the client configured in Keycloak 

|`MCP_SERVER_SECURITY_AUTH_PERMISSION`
|A string which defines the permission level to apply to the MCP Server endpoints. 
|`authenticated` (other values `permit`- default, `deny`)

|`MCP_SERVER_SECURITY_AUTH_SECRET`
|A string which holds the secret required to authenticate MCP Server with Keycloak. 
|`<your_client_secret>`, must match the secret from Keycloak. 

|`MCP_SERVER_SECURITY_AUTH_SERVER_URL`
|Points to the Keycloak realm used for authentication.
|`http://<keycloak-domain>/realms/{realm_name}`, the complete URL to your Keycloak realm

|`MCP_SERVER_OPENAPI_URLS`
|The OpenAPI v3 spec URI exposed for your _Business Service_
|`http://<yourhost>:<port>/q/openapi` for Quarkus based services, or `http://<yourhost>:<port>/v3/api-docs` for Spring Boot based services
|===

NOTE:: The `<keycloak-domain>` used must be the same across the complete stack, i.e., the {MCP_SERVER}, the _Business Service_ and the MCP Client. 

A sample is shown below:

[source, shell]
----
docker run -it --rm \
  -p 8080:8080 \
  --name mcp-server \
  -e MCP_SERVER_SECURITY_ENABLED=true \
  -e MCP_SERVER_SECURITY_OIDC_CLIENT_ID=kie-app \
  -e MCP_SERVER_SECURITY_AUTH_SECRET=secret \
  -e MCP_SERVER_SECURITY_AUTH_SERVER_URL=http://keycloak:8180/realms/kie \
  -e MCP_SERVER_SECURITY_AUTH_PERMISSION=authenticated \
  -e MCP_SERVER_OPENAPI_URLS="http://127.0.0.1:8080/q/openapi" \
  quay.io/bamoe/mcp-server:main
----

When started as images, the different components are visible to each other using the following Docker conventions:

* By default the domain of a service is the name of the service, e.g., if the service is called “keycloak”, the domain to be used in URL is keycloak,` http://keycloak…` 

* With out-of-the-box configuration, services are exposed at localhost IP (127.0.0.1). Inside docker configuration, this can be expressed with host.docker.internal (http://host.docker.internal…) 

* Since the MCP Client must use the same keycloak_domain as MCP Server and _Business Service_, you will need a DNS entry (“/etc/hosts”) in the running machine to map that domain to the IP under which Keycloak could be accessed. In the above example, the keycloak server is available at 127.0.0.1 and the keycloak_domain is set to “keycloak”; so, the /etc/hosts entry should be `127.0.0.1 keycloak`. 

=== Docker Compose example configuration
The following is an example of a Docker compose file that starts all the three required services (Keycloak, {MCP_SERVER}, _Business Service_):

[source, xml]
----
services:
  postgres:
    container_name: process-security-postgres
    image: postgres:16.8-alpine3.21
    profiles: [ "jvm", "container" ]
    ports:
      - "5432:5432"
    volumes:
      - ./docker-compose/sql:/docker-entrypoint-initdb.d:Z
    healthcheck:
      test: [ "CMD-SHELL", "pg_isready -U postgres -d postgres" ]
      timeout: 45s
      interval: 10s
      retries: 50
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      
  keycloak:
    container_name: bamoe-ai-keycloack
    image: quay.io/keycloak/keycloak:26.3
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      - KC_BOOTSTRAP_ADMIN_USERNAME=admin
      - KC_BOOTSTRAP_ADMIN_PASSWORD=admin
    ports:
      - 8080:8080
    volumes:
      - ./keycloack/bamoe-realm.json:/opt/keycloak/data/import/bamoe-realm.json
      - ./keycloack/kie-realm.json:/opt/keycloak/data/import/kie-realm.json
    command: [ "start", "--import-realm" ]
    restart: unless-stopped
    
  business-service:
    container_name: business-service
    image: dev.local/bamoe/process-security-kie-service:${PROJECT_VERSION}
    profiles: [ "container" ]
    depends_on:
      keycloak:
        condition: service_healthy
      postgres:
        condition: service_healthy
    environment:
      QUARKUS_HTTP_CORS_ORIGINS: "/.*/"
      QUARKUS_DATASOURCE_JDBC_URL: "jdbc:postgresql://127.0.0.1:5432/kie1"
      QUARKUS_DATASOURCE_REACTIVE_URL: "postgresql://127.0.0.1:5432/kie1"
      QUARKUS_DATASOURCE_USERNAME: kie-user-1
      QUARKUS_DATASOURCE_PASSWORD: kie-pass-1
      QUARKUS_DATASOURCE_DB_KIND: postgresql
      QUARKUS_HTTP_PORT: 8081
      KOGITO_JOBS_SERVICE_URL: http://${HOST}:8081
      KOGITO_SERVICE_URL: http://${HOST}:8081
      KOGITO_DATAINDEX_HTTP_URL: http://${HOST}:8081
      QUARKUS_OIDC_AUTH_SERVER_URL: http://${HOST}:8180/realms/kie
    network_mode: host

  mcp-server:
    container_name: mcp-server
    image: quay.io/bamoe/mcp-server:main
    depends_on:
      keycloak:
        condition: service_healthy
      business-service:
        condition: service_healthy  
    ports:
      - "8082:8080"
    environment:
      MCP_SERVER_SECURITY_ENABLED: true
      MCP_SERVER_SECURITY_OIDC_CLIENT_ID: kie-app
      MCP_SERVER_SECURITY_AUTH_SECRET: secret
      MCP_SERVER_SECURITY_AUTH_SERVER_URL: http://keycloak:8080/realms/kie
      MCP_SERVER_SECURITY_AUTH_PERMISSION: authenticated
      MCP_SERVER_OPENAPI_URLS: "http://host.docker.internal:8081/q/openapi"
      MCP_SERVER_DEBUG_LEVEL: INFO      
----

With the above file in place and the images and paths set up correctly, the whole system can be started with the following command:

[source, shell]
----
docker compose up
----

== Consuming a secured {MCP_SERVER}
After configuring the {MCP_SERVER}, your _Business Service_ with a Security layer, the following examples shows how the `MCP Inspector` (a NodeJS application that is an MCP-compatible client) provides a web application used to test, debug and consume the {MCP_SERVER}. Other MCP clients will support a process that may slightly differ from the one documented, see xref:https://modelcontextprotocol.io/clients[List of applications that support MCP Servers] for more information on your particular MCP client. 

. Launch your MCP client (`MCP Inspector`) by running the following command in your terminal:
+
[source, shell]
----
npx @modelcontextprotocol/inspector@latest
----

. Access the `MCP Inspector` available at `http://localhost:6274`
+
image::integrating-ai/mcp-inspector.png[width=600]

. Configure the connection with the {MCP_SERVER}:
* Set `Transport Type` to `Streamable HTTP(HTTP)`
* Set MCP Server URL to the URL of the port you configured for your {MCP_SERVER}

. In the Authentication section, add a new `Custom Header`, specifying `Authorization` as the header name and adding the bearer token (i.e. "Bearer my token...") as the header value. 

. In the `MCP Inspector` you can retrieve the list of tools offered by the MCP Server and execute them. 

NOTE:: When using an MCP client in an Agentic AI environment, during chat interactions, the LLM component of the AI Agent accesses the MCP Server tool list and executes the appropriate tools.
