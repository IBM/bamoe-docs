= Exposing {PRODUCT_SHORT} capabilities to AI agents

include::../styles/images.adoc[]

The {MCP_SERVER} provides a dedicated and isolated layer that actively exposes _Business Services_, including rule evaluation, decision models, and process orchestration, through a standardized interface optimized for agentic workflows. It is provided as a Docker image to facilitate deployment in the environment it will be used in. 

You can use it to build intelligent assistants, autonomous systems, or orchestrate complex business logic. It enables agents to reason, decide, and act with precision. By default, the {MCP_SERVER} runs without authentication, but from {VERSION} you can choose to enable security by configuring a set of environment variables that connect the server to a Keycloak realm (see xref:#configure-security[Configuring MCP Server Security]).

The {MCP_SERVER} exposes the following capabilities of _Business Services_: 

* Decision model execution (DMN)
* Rule model execution
* A Process API that allows agents to create, retrieve, modify, and delete process instances.

.Prerequisites 

* Run a _Business Service_ instance and the following setup:
** You can use a Quarkus or Spring Boot project (Spring Boot is not supported in {VERSION_930}).
** Enable OpenAPI v3 endpoints by adding the following entry to your `application.properties` file:
+
[source,properties]
----
quarkus.swagger-ui.always-include=true
----
+
NOTE: If you want to expose both the OpenAPI and Swagger endpoints you can also use the `quarkus.swagger-ui.always-include=true` instead. 
+
** Ensure the OpenAPI endpoint is at `\http://<host>:<port>/q/openapi/`. This is the only mandatory configuration required to activate the {MCP_SERVER}.
** Define meaningful names for models, fields, and nodes in _Business Services_ to improve the effectiveness of AI agent interactions.
** Configure rule models appropriately:
*** For RuleUnit based models, annotate each implemented `DataStore<>` class with `@Schema`, specifying the implementation class.
For example, in case of `DataStore<Person>` the annotation should be added as:
+
[source,properties]
----
@Schema(implementation = Person.class)
private DataStore<Person> persons;
----
+

*** For plain DRLs without RuleUnits, manually define and expose model endpoints, as they are not generated automatically.

* Use the `bamoe / mcp-server` image available in your container orchestration platform.

== Execution and lifecycle management

To run the {MCP_SERVER}, complete the setup and launch the server image in a Docker environment using the following command:

[source,shell, subs="attributes+"]
----
docker run -it --rm \
  -p 8081:8080 \
  --name mcp-server \
  -e MCP_SERVER_OPENAPI_URLS="http://host.docker.internal:8080/q/openapi" \
  quay.io/bamoe/mcp-server:{IMAGE_VERSION_930}
----

At startup, the MCP Server parses all exposed BAMOE Business Services and translates their capabilities into MCP Tools. These tools become available to any MCP-compatible client or agentic AI environment that supports the MCP protocol, allowing users to seamlessly integrate {PRODUCT_SHORT} automation features into AI-driven workflows.

Once running, the MCP Server begins serving requests from AI agents. Its internal state remains immutable, so any changes to the underlying Business Services are not automatically reflected. To apply updates, you must restart the MCP Server. A recommended approach is to use a reverse proxy to manage the lifecycle and handle image immutability internally.

Any MCP-compatible client that supports the MCP protocol can consume the {PRODUCT_SHORT} MCP Server. Examples include Goose, 5ire, LM Studio, and Claude Desktop.

Client configuration depends on the chosen MCP client, but typically the MCP Server is treated as an extension. To connect, provide the following details in the client’s extension section:

* Extension name: Any meaningful name
* Type: HTTP streamable
* Endpoint: MCP Server endpoint (`http://<host>:<port>/mcp`)

Where `<port>` defaults 80 for http or 443 for https, if you do not specify a specific port. 

NOTE: Server-Sent Events (SSE) is supported but deprecated, and Standard IO (STDIO) is not supported.

One of the most useful aspects of the MCP Tools is their integration with AI agents, such as large language models (LLMs). These agents can dynamically invoke decision models, rule engines, and process APIs, bringing {PRODUCT_SHORT} automation capabilities directly into agentic workflows.

== Configuring MCP Server Security

If the Business Service is also secured, it is essential to integrate the security layers of both the MCP Server and the Business Service. This ensures that the same access token used to authenticate with the MCP Server can be propagated and reused to securely access the Business Service. 

Thus, the suggested and supported scenario is when both Business Services endpoints and MCP server are secured under the same security layer, sharing the same credentials. Realm and credential configurations for this integration are described in the following sections.

This section outlines how to secure your MCP Server endpoints relying on OpenID Connect (OIDC) Provider, such us as Keycloak. 

Standalone Keycloak Server Setup

.Prerequisites 

* Keycloak must be accessible at a known domain.
* Realm must be configured with:
** client-id and client-secret.
** Users and roles.
** Token settings (expiration, scopes, etc.).

Other requirements specific to Keycloack (e.g. database used for persistence) are not part of {MCP_SERVER} {VERSION}

=== Import Realm Configuration:
If a realm configuration already exists, it may be imported in Keycloak at startup.

The following shows an example on how to launch a Keycloak instance in a docker environment.

[source, shell]
----
docker run -d \
 --name keycloak \
 -e KEYCLOAK_ADMIN=admin \
 -e KEYCLOAK_ADMIN_PASSWORD=admin \
 -e KC_IMPORT=/opt/keycloak/data/import/realm.json \   # Path inside container where realm file is mounted
 -v /path/to/realm.json:/opt/keycloak/data/import/realm.json \  # Replace with your actual file path
 -p 8443:8443 \
 quay.io/keycloak/keycloak:26.3 \
 start --optimized --import-realm
----

The following snippet shows the same command integrated into a `docker-compose.yml` file. 

[source, xml]
----
[...]
keycloak:
    container_name: keycloak
    image: quay.io/keycloak/keycloak:26.3
    environment:
      - KC_BOOTSTRAP_ADMIN_USERNAME=admin
      - KC_BOOTSTRAP_ADMIN_PASSWORD=admin
    ports:
      - 8443:8443
    volumes:
      - /path/to/{realm_name}-realm.json:/opt/keycloak/data/import/{realm_name}-realm.json
    command: [ "optimized", "--import-realm" ]
    restart: unless-stopped
----

Where `/path/to/{realm_name}-realm.json` is replaced by your actual file path.

=== Integrating Security accross {MCP_SERVER} and your _Business Services_
When both the MCP Server and the Business Service are secured, it's essential to integrate their security layers. 

The same access token used to authenticate the user with the MCP Server can also be used to securely access the Business Service.

The MCP Server can forward the token when calling Business Service endpoints, maintaining a consistent and trusted identity across services.

This avoids requiring the user to authenticate separately for each service and enables seamless, secure communication between components.

In short: Token propagation is required so that the Business Service trusts requests coming from the MCP Server on behalf of the authenticated user.

Make sure that the following configurations are in place to ensure secure communication between the MCP Server and the Business Service, when both are under security.

Shared Realm and Credentials - To ensure secure communication and consistent authentication, irrespective of if the Business Service is Quarkus Based or Spring Boot Based, both the MCP Server and the Business Service must use the same Keycloak realm and credentials.

Both services use the same:

client-id: <your_client_id>

client-secret: <your_client_secret>

Realm: <your_realm_name>

Domain: keycloack_domain

       This allows both services to validate users using the same identity provider.

In the Securing Business Service API endpoints page, a guide that explain how to enable the security layer for a Business Service instance. Once that configuration is well defined, the same parameters should be reused for configuring the MCP Server Security layer, as described in the next paragraph.

=== MCP Server Image Configuration

When deploying the MCP Server using a Docker image, configure security using environment variables :

MCP_SERVER_SECURITY_ENABLED: A boolean that determines whether to enable the security layer. Default is false

MCP_SERVER_SECURITY_OIDC_CLIENT_ID = A string which defines the client_id for the authentication process. Value must match the client configured in Keycloak.

MCP_SERVER_SECURITY_AUTH_PERMISSION = A string which defines the permission level to apply to the MCP Server endpoints. Default is "permit", Possible values are: "permit", "authenticated" and "deny". 

MCP_SERVER_SECURITY_AUTH_SECRET = A string which holds the secret required to authenticate MCP Server with Keycloak. Use the secret from Keycloak.

MCP_SERVER_SECURITY_AUTH_SERVER_URL = Points to the Keycloak realm used for authentication. Complete URL to your Keycloak realm needs to be provided.

With MCP_SERVER_SECURITY_ENABLED=true and AUTH_PERMISSION=authenticated, all /mcp/* endpoints will be under security and require a valid Bearer token for authentication.

The token must be issued by the Keycloak realm specified in AUTH_SERVER_URL.

Example configuration with security enabled:

MCP_SERVER_SECURITY_ENABLED=true

MCP_SERVER_SECURITY_OIDC_CLIENT_ID=<your_Client_id>

MCP_SERVER_SECURITY_AUTH_PERMISSION=authenticated

MCP_SERVER_SECURITY_AUTH_SECRET=<your_client_secret>

MCP_SERVER_SECURITY_AUTH_SERVER_URL= http://<keycloak-domain>/realms/{realm_name}

MCP_SERVER_OPENAPI_URLS=” {business_service_url}/{openapi_path}"

Important note: the <keycloak-domain> must be exactly the same used over all the stack, i.e.

MCP Server

Business Service

MCP Client

These properties have to be set when the server start up.

A sample for the same is shown below:

[source, shell]
----
docker run -it --rm \
  -p 8080:8080 \
  --name mcp-server \
  -e MCP_SERVER_SECURITY_ENABLED=true \
  -e MCP_SERVER_SECURITY_OIDC_CLIENT_ID=kie-app \
  -e MCP_SERVER_SECURITY_AUTH_SECRET=secret \
  -e MCP_SERVER_SECURITY_AUTH_SERVER_URL=http://keycloak:8180/realms/kie \
  -e MCP_SERVER_SECURITY_AUTH_PERMISSION=authenticated \
  -e MCP_SERVER_OPENAPI_URLS="http://127.0.0.1:8080/q/openapi" \
  quay.io/bamoe/mcp-server:main
----

The following snippet shows the same command integrated into a `docker-compose.yml` file. 

[source, xml]
----
[...]
  mcp-server:
    container_name: mcp-server
    image: quay.io/bamoe/mcp-server:main
    depends_on:
      keycloak:
        condition: service_started
    ports:
      - "8080:8080"
    environment:
      MCP_SERVER_SECURITY_ENABLED: true
      MCP_SERVER_SECURITY_OIDC_CLIENT_ID: kie-app
      MCP_SERVER_SECURITY_AUTH_SECRET: secret
      MCP_SERVER_SECURITY_AUTH_SERVER_URL: http://keycloak:8180/realms/kie
      MCP_SERVER_SECURITY_AUTH_PERMISSION: authenticated
      MCP_SERVER_OPENAPI_URLS: "http://127.0.0.1:8081/q/openapi"
      MCP_SERVER_DEBUG_LEVEL: INFO
----

It is important to note the following:

* When started as images, the different components are visible to each other using the Docker convention, i.e. the domain of a service, by default, is the name of the service itself; e.g. if the service is called “keycloak”, the domain to be used in URL is keycloak (http://keycloak…) 

* With out-of-the-box configuration, services are exposed at localhost IP (127.0.0.1); inside docker configuration, this could be expressed with host.docker.internal (http://host.docker.internal…) 

* Since the MCP Client must to use the same keycloack_domain as MCP Server and Business Service, there is a need of a DNS entry (“/etc/hosts”) in the running machine to map that domain to the IP under which Keycloak could be accessed; in the above example, keycloak server is available at 127.0.0.1 and the keycloak_domain is set to “keycloak”; so, the /etc/hosts entry should be 127.0.0.1 keycloack. 

=== Docker-compose example configuration
The following is an example of a docker compose file that starts all the three required services (Keycloak, MCP Server, Business Service):

[source, xml]
----
services:
  postgres:
    container_name: process-security-postgres
    image: postgres:16.8-alpine3.21
    profiles: [ "jvm", "container" ]
    ports:
      - "5432:5432"
    volumes:
      - ./docker-compose/sql:/docker-entrypoint-initdb.d:Z
    healthcheck:
      test: [ "CMD-SHELL", "pg_isready -U postgres -d postgres" ]
      timeout: 45s
      interval: 10s
      retries: 50
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      
  keycloak:
    container_name: bamoe-ai-keycloack
    image: quay.io/keycloak/keycloak:26.3
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      - KC_BOOTSTRAP_ADMIN_USERNAME=admin
      - KC_BOOTSTRAP_ADMIN_PASSWORD=admin
    ports:
      - 8080:8080
    volumes:
      - ./keycloack/bamoe-realm.json:/opt/keycloak/data/import/bamoe-realm.json
      - ./keycloack/kie-realm.json:/opt/keycloak/data/import/kie-realm.json
    command: [ "start", "--import-realm" ]
    restart: unless-stopped
    
  business-service:
    container_name: business-service
    image: dev.local/bamoe/process-security-kie-service:${PROJECT_VERSION}
    profiles: [ "container" ]
    depends_on:
      keycloak:
        condition: service_healthy
      postgres:
        condition: service_healthy
    environment:
      QUARKUS_HTTP_CORS_ORIGINS: "/.*/"
      QUARKUS_DATASOURCE_JDBC_URL: "jdbc:postgresql://127.0.0.1:5432/kie1"
      QUARKUS_DATASOURCE_REACTIVE_URL: "postgresql://127.0.0.1:5432/kie1"
      QUARKUS_DATASOURCE_USERNAME: kie-user-1
      QUARKUS_DATASOURCE_PASSWORD: kie-pass-1
      QUARKUS_DATASOURCE_DB_KIND: postgresql
      QUARKUS_HTTP_PORT: 8081
      KOGITO_JOBS_SERVICE_URL: http://${HOST}:8081
      KOGITO_SERVICE_URL: http://${HOST}:8081
      KOGITO_DATAINDEX_HTTP_URL: http://${HOST}:8081
      QUARKUS_OIDC_AUTH_SERVER_URL: http://${HOST}:8180/realms/kie
    network_mode: host

  mcp-server:
    container_name: mcp-server
    image: quay.io/bamoe/mcp-server:main
    depends_on:
      keycloak:
        condition: service_healthy
      business-service:
        condition: service_healthy  
    ports:
      - "8082:8080"
    environment:
      MCP_SERVER_SECURITY_ENABLED: true
      MCP_SERVER_SECURITY_OIDC_CLIENT_ID: kie-app
      MCP_SERVER_SECURITY_AUTH_SECRET: secret
      MCP_SERVER_SECURITY_AUTH_SERVER_URL: http://keycloak:8080/realms/kie
      MCP_SERVER_SECURITY_AUTH_PERMISSION: authenticated
      MCP_SERVER_OPENAPI_URLS: "http://host.docker.internal:8081/q/openapi"
      MCP_SERVER_DEBUG_LEVEL: INFO      
----

With the above file in place and the images and paths set up correctly, the whole system could be started with the following command:

[source, shell]
----
docker compose up
