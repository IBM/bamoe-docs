= Migrating Process Instances using BAMOE PIM Add-on
include::../_partials/attributes.adoc[]
include::../_styles/images.adoc[]

When Process Definitions are deployed as _Business Services_ in a Cloud environment, client applications or {MANAGEMENT_CONSOLE} users can create Process Instances that follow the sequence flow defined in the Process Definition. Some Process Instances may run for weeks or months and be in waiting states, due to Timers or User Tasks. When deploying a new version of the Process Definition to running _Business Services_, you can use the {PIM_ADDON} to manage Process Instances in waiting states, and avoid them following obsolete Process Definitions. 

== Introduction to {PIM_ADDON}

The {PIM_ADDON} and its user interface enable you to manage the migration of in-flight Process Instances to a new Process Definition version or to a completely different Process Definition via:

* REST API and the {MANAGEMENT_CONSOLE} in the Runtime environment, 
* {QUARKUS_DEV_UI} or {SPRING_WEB_CONSOLE} in Dev environment. 

By mapping the original Process Definition nodes to updated Process Definition nodes, Process Instances can transition to the new sequence flow and adapt to changes in their definitions over time without losing their current state or requiring a restart.

This functionality enables you to:

* Keep long-running processes aligned with evolving business rules and business needs.
* Reduce operational risk by replacing obsolete workflows.
* Maintain flexibility to adapt your processes without restarting Process Instances.

== Migration guidelines
There are different ways to manage the evolution of Process Definition inside your _Business Service_, see xref:../10-managing-and-monitoring-business-services/migration-with-pim.adoc#evolving-deployed-workflows[Evolving stateful Workflows across _Business Service_ deployments]. The recommended way is to update your BPMN Process Definition, incrementing the version number then deploying your new Business Service version, therefore ensuring *one Business Service, one version*. You can then use PIM to migrate across Business Service deployments. 

A migration plan should be developed on a mirror of your production system. Before doing the actual migration, you should backup your database and plan downtime for your users to avoid conflicting changes on the same processes. Performing a Process Instance Migration on a live system could result in errors, and even data corruption. Only restore access once the migration has finished executing.

The hierarchy between a Process and its subprocesses is preserved during migration. When a Process Instance is migrated, all its subprocesses, including nested ones, are also automatically migrated. Alternatively, if you attempt to migrate a subprocess without migrating its parent process, the migration will fail.

NOTE: The new version of the Process Definition must be compatible with the previous version. If this is not the case you may have errors during the next interaction with Process Instances that have been migrated. In this situation you will need to use PIM to migrate Process Instances again to a compatible data model. 

=== Step by step PIM migration across different Business Service deployments
The following sections step you through the recommended way of migrating in-flight Process Instances in a Runtime system, starting from the baseline deployed Version 1.0 (e.g., `hiring:1.0`) of your _Business Service_ with active Process Instances:

. In _Business Service_ Version 2.0, update the BPMN and increment the model Version (`hiring:2.0`). To enable PIM migration you will also need to include the required PIM dependencies, see xref:../12-reference/maven-repository-libraries.adoc#PIM-addon-dependency[Maven Repository libraries → {PIM_ADDON_SHORT}] and enable with Data isolation, see xref:../08-developing-stateful-workflows/database-considerations.adoc#data-isolation-shared-databases[Database considerations → Data isolation on shared databases]..

. Deploy Business Service 2.0 containing `hiring:2.0`. Validate that is starts correctly and connects to the shared database.

. In the {MANAGEMENT_CONSOLE}, *All Business Services* mode, create a *Remote* migration plan, selecting the source Process Definition from Business Service 1.0 and the target Process Definition from Business Service 2.0. 

. Configure the explicit node mappings between the two Process Definitions using the UI provided. 

. Click *Create PIM Plan* and review the validation summary, addressing any warnings or errors before proceeding. 

. Test your migration plan on a duplicate of your Production system. 

. When you are ready to migrate your Production system, ensure you have isolated it from user interactions and that you have a recent backup.

. Migrate the Process Instances that are in a wait state and that match the defined criteria, to the new Process Definitions, in one of the following ways:

.. Execute the required PIM plan (Local, Remote or Installed - if they exist for the _Business Service_) manually using the {MANAGEMENT_CONSOLE}, see xref:consoles.adoc#process-instance-migration-ui[Management Console → Process Instance Migration].

.. Execute the required PIM plan (Local, Remote or Installed - if they exist for the _Business Service_) using REST API, see xref:#pim-migration-rest[Process to migrate via REST API]. 

.. Use the Automatic PIM migration functionality to deploy a new Business Service version that automatically migrates previous versions of the Business Service, see xref:#auto-migration[Using installed migration plans to dynamically activate PIM migration]

. During migration, the state of a Process Instance is preserved and Process and Task variables, Jobs schedules and SLAs remain unchanged. 

. If an error occurs do the following:

.. Restore the database from the backup taken before execution.
.. Remove Business Service v2 and reconnect Business Service v1.
.. Review the migration plan and deploy a corrected Business Service v2 before retrying.

. After validating that Business Service v2 is working correctly with the migrated instances, decommission Business Service v1. Business Service v2 is now your new baseline, containing only `hiring:2.0`.

If you are using Quarkus, your migrations can take time due to heavy database updates. You can configure the following transaction timeout in `application.properties`:

[source,properties]
----
bamoe.pim.transaction-timeout=<seconds>
----

If you are experiencing slowness during the PIM execution with PostgreSQL, make sure that database statistics are up-to-date by running `ANALYZE`, or disable nested loop joins in the database:

[source,properties]
----
enable_nestloop=off
----

=== Managing migration plans
There are different ways of setting up your migration plans depending on how you are managing the evolution of your BPMN Process Definition inside _Business Services_. Plans can be: 
* *Local* where the source and target BPMN are contained in the same _Business Service_, 
* *Remote* where the source BPMN Process Definitions originates from a different _Business Service_. 
* *Installed* where the plan is exported and executed automatically on startup of a newly deployed _Business Service_ version. 

More details on the differences between each are detailed in the table below:

=== What happens during migration?
PIM does more than just switch Process Definitions; it ensures consistency across the stateful process subsystems in the following ways:

Subsystem adaptation:: Migrates process nodes and updates associated elements across subsystems, including Data-Index, User Tasks, and the Jobs Service schema, as well as all additional process reference columns introduced by data isolation. After migration, the _Business Service_ remains fully functional through both REST APIs and UIs.

Active elements only:: Only active elements (node instances, User Tasks, etc.) are migrated. Nodes that are no longer active will not be migrated.

Data handling:: Process Instances contain information (data) about the entities in the Workflow, necessary to execute the Workflow (Process or Task variables), and that PIM does not migrate. If your new Process Definition contains new variables, they will be initialized with an empty value. If your data model changes, you must ensure backward compatibility, otherwise, PIM cannot properly migrate Process Instances, and you will need to use alternative strategies, such as draining out existing instances. 

=== Mapping rules and limitations

To maintain process integrity after migration, PIM has some strict node mapping rules, applied via implicit or explicit node mappings.

Implicit node mapping:: All nodes that can be on a waiting state in the source process definition must exist in the target process definition with their original node ID.

Explicit node mapping:: When implicit mapping is not satisfied you need to provide explicit node mappings.

The following table describes the rules for *Explicit Node mappings*:

[cols="1,1a"]
|===
| *Explicit node mapping rules* 
| *Description*

|*Nodes type*
|Only nodes that can put the Process Instance in a waiting state (catch events, user tasks, work items, call activities/subprocesses) should be included in the explicit mapping list, since only active elements are migrated.

|*Same family mapping*
|Nodes must be mapped to nodes of the same type. For example, a User Task cannot be mapped to an event.

|*Removed nodes*
|If a node is removed in the target Process Definition, the source node must be explicitly mapped to a node of the same family in the target Process Definition.

|*User Task limitation*
|Tasks in BPMN are immutable in the User Task subsystem. To modify task details during migration, define a new task with a different ID and node ID in the target Process Definition and map accordingly.

|*Implicit mapping must become explicit*
|If a node must be explicitly mapped in the plan, any implicit mapping must become explicit. In this case, the BAMOE PIM Add-on automatically converts implicit mappings to explicit mappings, adding them to the plan.

|===

== Process Instance migration through the PIM REST API
If you want to automate or integrate migration in a larger process, rather than complete the migration using the UI, {PRODUCT_SHORT} exposes a REST API for Process Instance Migration, see xref:management-apis.adoc#process-instance-migration-addon[Management APIs Process → Process Instance Migration APIs]. 

The following endpoints are used to create and manage migration plans with the PIM Add-on:

. Create a new migration plan that defines how process instances move from a source process to a target process using `POST /pim/plan`, defining the following payload fields:
+
* name (String) - The `name` field provides you with a human-readable label to distinguish uniquely identify the plan. 
* sourceProcessId (String) - ID of the source process.
* sourceProcessVersion (String) - Version of the source process.
* targetProcessId (String) - ID of the target process.
* targetProcessVersion (String) - Version of the target process.
* sourceProcessXml (String) - The parsed source BPMN XML for Remote migration plans since the target _Business Service_ has no local access to the source BPMN file (see xref:#remote-migration-plan[Using Remote migration plans])
* nodeMapping (List) - Optional list of node mappings (sourceId →
targetId). 
+
For example:
+
[source,JSON]
----
 {
   "name": "hiring migration 1.0 to 2.0",
   "sourceProcessId": "hiring",
   "sourceProcessVersion": "1.0",
   "targetProcessId": "hiring2",
   "targetProcessVersion": "1.0",
   "sourceProcessXml":  "<?xml version=\"1.0\" ...><definitions ...>...</definitions>",
   "nodeMapping": [
     {"sourceId": "_B8C4F63C-81AD-4291-9C1B-84967277EEF6", "targetId": "_CBB6BF5D-21DA-43D2-A20B-C361694AF7AE"},
     {"sourceId": "_B4BB21C5-7BCA-47DA-A688-2F37BC6B76A7", "targetId": "_C7DBD2B3-1744-4844-8B3D-D23CAF9D2436"}
]
 }
----
+
The endpoint returns the plan details, validation status, and warnings/errors if any.

. You can use `GET /pim/plan/{planId}` to obtain details of a specific migration plan, including mappings and validation results.

. You can use `DELETE /pim/plan/{planId}` to remove a migration plan that is not currently in use. 

. You can use `GET /pim/plans` to retrieve all migration plans, and optionally filter using the `sourceProcessId` and `targetProcessId` as query parameters. 

More endpoints are available for *Remote* and *Installed* PIM plans.

=== Managing migrations 
You can use the following endpoints to execute and retrieve information on migrations with the PIM Add-on:

You can use `POST /pim/migration` to execute the migration of active Process Instances from the source to the target Process Definition using the specified migration plan.

* If you want a full migration where all active Process Instances of the source process are migrated, do not specify any Process Instance IDs.
+
* If you want a bulk migration to migrate a subset of Process Instances, provide a list of Process Instance IDs to be included in the bulk migration.
+
Each database has a maximum number of parameters allowed in an update operation. This affects how many process instance IDs you can include in a bulk migration request. Below are the limits for each supported database:

** H2 → 50,000 IDs
** PostgreSQL → 50,000 IDs
** Oracle → 1,000 IDs
** MS SQL Server → 2,000 IDs
** Db2 →  32,000 IDs

For example:

[source,json]
----
 {
   "planId": "<plan_id>",
   "processInstanceIds": ["id1", "id2", "id3", ...]
}
----

Which returns the following:


[source,json]
----
 {
   "status": 200,
   "message": "Migration finished",
   "data": {
     "migrationId": "<migration_id>",
     "planId": "<plan_id>",
      "migratedProcessInstancesCount": 100000
   }
 }
----

Where:

migrationId:: is the unique identifier for the migration.

migratedProcessInstancesCount:: is the number of instances migrated.

skippedProcessInstanceIds:: lists any IDs that were not migrated, if they exist.

You can use `GET /pim/migration/processes/{processInstanceId}` to return the list of migrations associated with a given Process Instance, including timestamps for when the migration was created and applied.

[source, json]
----
 {
   "status": 200,
   "message": "Retrieved migrated process instance",
   "data": [
     {
       "migrationId": "<migration_id>",
       "processInstanceId": "<process_instance_id>",
       "planId": "<plan_id>",
       "createdAt": "2025-11-20T00:00:00.000+00:00",
       "appliedAt": "2025-11-20T15:23:58.910+00:00"
} ]
}
----

You can use `GET /v1/migrations/plans/{planId}/export?includeSourceProcessXml=true` to download a plan as a self-contained JSON spec file that can be used as an Installed plan (see xref:##auto-migration[Automatic migration on startup using Installed plans]). 

The server responds with `Content-Disposition: attachment; filename=<sourceId>-<srcVer>-to-<targetId>-
<tgtVer>.json`. Setting `includeSourceProcessXml=true` embeds the BPMN XML in the file; this is useful when
exporting a plan created in a staging environment to be installed on production.

NOTE: Export is not available for Installed plans. Only Local and Remote plans can be exported via the REST API.

[#remote-migration-plan]
== Using Remote migration plans to migrate across Business Service deployments
A *Remote* migration plan is one where the source and target Process Definitions are contained in different _Business Service_ deployments. This enables you to manage the evolution of your Business Service Process Definitions as recommended in xref:../09-building-and-deploying-business-services/services-deployment.adoc#evolving-deployed-workflows[Evolving stateful Workflows across _Business Service_ deployments], namely **one Business Service, one version**.

Migration across two _Business Service_ deployments requires both _Business Services_ to connect to the same database. The {PIM_ADDON_SHORT} in the target _Business Service_ must be able to read Process Instances, User Tasks, and Jobs that were created by the source _Business Service_, which is only possible when both services share the same underlying database and data isolation is enabled, see xref:../08-developing-stateful-workflows/database-considerations.adoc#data-isolation-shared-databases[Database considerations → Data isolation on shared databases]

You can use the `sourceProcessXml` field to provide the BPMN XML of the source process. PIM parses and validates the XML at plan-creation time and stores it in a dedicated table: `bamoe_process_instance_migration_plan_remote_source_process_definitions`. All subsequent migrations will use the stored XML so the original service does not need to be reachable on deployment.

The target Process Definition must be in the newly deployed _Business Service_ which contains the runtime that will execute the migrated instances. Remote Process Definitions are immutable. Once a *Remote* plan is created the stored XML cannot be changed. To update the source definition, delete the plan and create a new one.

All **Job instances** associated with the Process Instances being migrated are also migrated. This ensures that scheduled timers and events continue to work correctly after migration.

=== Creating a Remote plan via API

Include `sourceProcessXml` in the request body when you call `POST /plans`. The field must contain a valid, well-formed BPMN 2.0 document.

[source,json]
----
POST /v1/migrations/plans
Content-Type: application/json

{
  "sourceProcessId":      "hiring",
  "sourceProcessVersion": "1.0",
  "targetProcessId":      "hiring",
  "targetProcessVersion": "2.0",
  "sourceProcessXml":     "<?xml version=\"1.0\" ...><definitions ...>...</definitions>",
  "nodeMapping": [
    { "sourceId": "_node-A", "targetId": "_node-A" }
  ]
}
----

The response includes a `planType` field set to REMOTE:

[source,json]
----
{
  "id":                   "3fa85f64-...",
  "sourceProcessId":      "hiring",
  "sourceProcessVersion": "1.0",
  "targetProcessId":      "hiring",
  "targetProcessVersion": "2.0",
  "planType":             "REMOTE",
  "updatedAt":            "2026-07-31T10:00:00Z"
----

You can use `GET /v1/migrations/plans/{planId}?detailed=true` to retrieve the source BPMN XML including the `sourceProcessXml` for *Remote* plans. 

[#auto-migration]
== Automatic migration on startup using Installed plans 
Migration of in-flight Process Instances can be done manually (via the PIM REST API or the Management Console) or migration can be automatically triggered when an updated _Business Service_ with a new Process Definition is deployed. 

To do this you create an *Installed* migration plan, defined by a JSON spec file (e.g. `001-hiring-v1-to-v2.json`) that can be placed in a directory that is mounted into the pod. When a newly deployed _Business Service_ has the property `bamoe.pim.migrate-on-start.enabled=true` PIM reads all `*.json` files from that directory at startup, validates them as a batch, and executes the migrations.

You can use `GET /v1/migrations/plans/{planId}/export?includeSourceProcessXml=true` to download a plan as a self-contained JSON spec file that can be used as an *Installed* plan. 

Installed plans differ from *Local* and *Remote* plans in the following ways:

* They cannot be created, updated, or deleted via the REST API. 
* The lifecycle is entirely controlled through the spec
files on disk.
* Each file is identified by its filename and a SHA-256 checksum. If a pod restarts and finds a plan with the same
filename and checksum already in the database it reuses the existing record (idempotent).
* They are not exportable via the /export endpoint.

For more information on how to export a plan in the {MANAGEMENT_CONSOLE} see xref:consoles.adoc#export-plan-console
[Exporting a plan to be used as an Installed plan]

=== Installed plan JSON spec file format

Each *Installed* plan file must be valid JSON matching the PlanSpec schema:

[source,JSON]
----
{
  "sourceProcessId":      "hiring",
  "sourceProcessVersion": "1.0",
  "targetProcessId":      "hiring",
  "targetProcessVersion": "2.0",
  "nodeMapping": [
    { "sourceId": "_node-A", "targetId": "_node-A" }
  ]
}
----

Files are processed in alphabetical order, so prefixing filenames with a numeric index gives deterministic ordering: 001-hiring-v1-to-v2.json, 002-approval-v2-to-v3.json, …

You can use `GET /v1/migrations/plans/{planId}/export` to download a *Local* or *Remote* plan from an existing plan, as a ready-to-use spec file 
Use .

=== Enabling migration on startup for your Business Service
The Automatic migration feature is disabled by default. To enable it for your _Business Service_ you will need to set the following properties in the `application.properties` file:

[%header,cols=4]
[%autowidth]
|===
| Property
| Type
| Default 
| Description

|`bamoe.pim.migrate-on-start.enabled`
|boolean
|`false`
|Enables the migrate-on-start feature. Set to true to activate.

|`bamoe.pim.migrate-on-start.plans-path`
|string
|`/opt/pim/plans`
|Absolute path to the directory containing *.json spec files

|`bamoe.pim.transaction-timeout`
|`int (seconds)`
|3600
|Quarkus only. Maximum wall-clock seconds for the migration transaction. Increase for large datasets.
|===

The following shows an example configuration for Quarkus:

[source,xml]
----
# application.properties
bamoe.pim.migrate-on-start.enabled=true
bamoe.pim.migrate-on-start.plans-path=/opt/pim/plans
bamoe.pim.transaction-timeout=3600
----

The following shows an example configuration for Spring Boot:

[source,xml]
----
# application.properties
bamoe.pim.migrate-on-start.enabled=true
bamoe.pim.migrate-on-start.plans-path=/opt/pim/plans
----

=== Deploying Installed plans on Kubernetes/OpenShift

In order to make your Installed migration plans available to new Business Service versions at deployment you will need to mount a ConfigMap or Secret that contains your spec files at the configured plans-path. You can see a simple example below:

[source,JSON]
----
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
        - name: business-service
          env:
            - name: BAMOE_PIM_MIGRATE_ON_START_ENABLED
              value: "true"
            - name: BAMOE_PIM_MIGRATE_ON_START_PLANS_PATH
              value: /opt/pim/plans
          volumeMounts:
            - name: pim-plans
              mountPath: /opt/pim/plans
              readOnly: true
      volumes:
        - name: pim-plans
          configMap:
            name: my-pim-migration-plans
----


=== Health / readiness probe

The {PIM_ADDON_SHORT} automatically registers a readiness check named `startup-migration` when the feature is enabled.

[%header,cols=2]
[%autowidth]
|===
|Migration status	
|Readiness response

|RUNNING	
|DOWN — pod not yet ready to serve traffic

|SUCCESS	 
|UP - pod is ready

|FAILURE	
|DOWN — pod will shut down

|disabled	
|UP — feature off, always passes
|===


If you enable migrate-on-start on a deployment that uses rolling updates, the first pod to start becomes the migration executor. Subsequent pods will wait on the lock. Ensure your liveness probe timeout is longer than your expected worst-case migration duration to prevent premature restarts.

=== Batch validation rules

Before any migration is executed, {PIM_ADDON_SHORT} validates the full set of Installed plan spec files together and reports all violations in a single error message. If any rule is violated the entire startup migration is aborted and the application shuts down:

[%header,cols=2]
[%autowidth]
|===
|Rule	
|Description

|Required fields	
|All four coordinate fields (`sourceProcessId`, `sourceProcessVersion`, `targetProcessId`, targetProcessVersion``) must be present and non-blank.

|Duplicate sources	
|No two Installed plan spec files may share the same `sourceProcessId` + `sourceProcessVersion` pair.

|Self-loop	
|Source and target coordinates must not be identical.

|Bidirectional cycle	
|The Installed plan spec list must not contain specs A→B and B→A simultaneously.

|Target process deployed	
|Each target process must be deployed in the running _Business Service_ at the declared version.
|===

=== The startup sequence
Once a new _Business Service_ is deployed with the required settings for automatic migration on startup, the following sequence is followed to trigger migration in a multi-pod environment:

. Readiness gate: The pod's readiness probe reports NOT READY while migration is in progress, preventing traffic from
reaching a pod that has not yet migrated its instances.
. Distributed lock acquisition: All replicas race to INSERT a row into
`bamoe_process_instance_migration_startup_lock`. The first to succeed becomes the executor; all others
become waiters.
. Batch validation: The executor validates all spec files as a group, checking for missing required fields, duplicate source
coordinates, self-loop migrations, bidirectional cycles, and target processes not deployed in the current runtime.
. Sequential execution: Each spec is registered as an *Installed* plan (or reused if already present) and
`migrateAllProcessInstances` is called in an independent transaction.
. Lock release: The executor updates the lock row to SUCCESS or FAILURE and the readiness probe transitions
accordingly. Waiter pods read the terminal status and unblock.
. Failure handling: On FAILURE the application initiates a graceful shutdown. The operator must resolve the underlying
issue, clear the lock row, and redeploy.

NOTE: Lock row must be cleared manually after a FAILURE. PIM does not automatically retry a failed startup migration. Delete the row from `bamoe_process_instance_migration_startup_lock` where `lock_key groupId:artifactId:version` before redeploying.
