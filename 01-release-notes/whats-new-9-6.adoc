== Workflow engine - Workflow versioning
{PRODUCT_SHORT} {VERSION} now supports the creation and deployment of a new version of a Process Definition with the same ID and and a new Version number. In previous versions of {PRODUCT_SHORT} {VERSION_X} versioning was done via the Process ID, and updating a workflow generated multiple IDs (e.g., hiring, hiring2, etc.) requiring updates to your client applications to use new endpoints (e.g., /hiring to /hiring2). The ability to manage multiple versions with the same ID streamlines the process to migrate Process Instances to a new version of the Process Definition. 

xref:../09-building-and-deploying-business-services/services-deployment.adoc#evolving-deployed-workflows[Learn more...]

== Automatic execution of {PIM_ADDON} to migrate _Business Services_ on startup
When deploying a new version of the Process Definition automatically via a CI/CD pipeline
there is often no simple way to migrate in-flight Process Instances to a new version of the Process Definition
as part of the deployment. To address this, {PRODUCT_SHORT} {VERSION} can now trigger the {PIM_ADDON} automatically on Business Service startup, via migration plans that are specified in JSON files, enabling you to use your existing CI/CD pipelines without the need for complex modifications. {PIM_ADDON_SHORT} automatically registers those plans and migrates all matching active Process Instances, ensuring distributed locking to guarantee exactly-once execution across replicas. xref:../10-managing-and-monitoring-business-services/migration-with-pim.adoc[Learn more...]

== Workflow engine - Data isolation for _Business Services_ connected to a single database

When multiple _Business Services_ within the Compact Architecture configuration, they may share the same database. In the previous versions of {PRODUCT_SHORT} the persistence subsystems — Data Index, Jobs Service, Data Audit, User Task storage, and Process Instance storage were able to read data from any _Business Service_ in that shared database, causing data leakage between services. To avoid this each _Business Service_ required its own database. 

In {PRODUCT_SHORT} {VERSION_RM}, you are are now able to activate data isolation between services with a single configuration property: `kogito.persistence.data-isolation.enabled=true`. When enabled, each _Business Service_ automatically filters all database queries to return only its own data. The filtering happens at the SQL level and no additional network calls or external services are required.

xref:../08-developing-stateful-workflows/database-considerations.adoc[Learn more...]

== New Role-based access control for Business Services in production
{PRODUCT_SHORT} {VERSION} provides fine-grained role-based access control (RBAC) at a _Business Service_ level to control access through the Management Console or API. Features can now be restricted by user role, enabling enterprises to enforce read-only or read/write access per capability. Permissions are sourced from the Identity Provider, ensuring centralized governance and compliance.

Using the new Role-based Access Control you are now able to:

- Specify which Management Console pages or actions are visible for specific user profiles depending on their permissions.
- Protect the underlying Business Service REST and GraphQL endpoints by role.
- Utilize existing role definitions defined by the OpenID Connect (OIDC) Identity Provider that your organization uses (Keycloak, Auth0, Okta, or Azure AD).

The capability is provided through two new add-ons: 

{RBAC_ADDON}:: Exposes user permissions to the Management Console via a `/me` endpoint, and optionally cross-checks permissions against the Business Service's route security. 

BAMOE RBAC Data-Index Add-on:: Enforces role-based access on the Data Index GraphQL endpoint (`/graphql`).

xref:../09-building-and-deploying-business-services/security.adoc[Learn more...]

== Database password encryption in BAMOE container images
With {PRODUCT_SHORT} {VERSION}, the {DATA_CLEANUP} now offers
two new ways to supply database credentials: encrypted (AES-GCM, decrypted by the tool at
startup), and Vault (fetched from HashiCorp Vault when the tool starts). The tool decides which
mode to use based on environment variables set. No configuration file changes are needed. xref:../10-managing-and-monitoring-business-services/managing-runtime-data.adoc[Learn more...]

== Support for dynamic Subprocess invocation
{PRODUCT_SHORT} {VERSION} includes support for dynamic subprocess calls, where the identifier of the called
subprocess is set at runtime in a process variable. This feature was supported by {PRODUCT_SHORT} 8, and the availability of this feature in {VERSION} facilitates migration of BAMOE 8 applications to this version. xref:../xxxx.adoc[Learn more...]
