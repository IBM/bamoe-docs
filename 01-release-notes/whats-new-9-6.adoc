== Workflow engine - Data isolation for _Business Services_ connected to a single database

When multiple _Business Services_ within the Compact Architecture configuration, they may share the same database. In the previous versions of {PRODUCT_SHORT} the persistence subsystems — Data Index, Jobs Service, Data Audit, User Task storage, and Process Instance storage were able to read data from any _Business Service_ in that shared database, causing data leakage between services. To avoid this each _Business Service_ required its own database. 

In {PRODUCT_SHORT} {VERSION_VM}, you are are now able to activate data isolation between services with a single configuration property: `kogito.persistence.data-isolation.enabled=true`. When enabled, each _Business Service_ automatically filters all database queries to return only its own data. The filtering happens at the SQL level and no additional network calls or external services are required.

xref:../08-developing-stateful-workflows/database-considerations.adoc[Learn more...]


== Workflow engine - Workflow versioning
Due to historical limitations, workflow versioning in {PRODUCT_SHORT} 9 is done using the process ID, meaning that evolving a workflow will generate multiple IDs (e.g., hiring, hiring2, and so on). The workflow engine generates endpoints based on the process ID of a workflow. By changing the workflow process ID, customers are required to update their client applications to use new endpoints (for example, update /hiring to /hiring2).
 

To address routing between multiple Business Services, {PRODUCT_SHORT} {VERSION} introduces a new capability called "Routing Management". This capability will focus on managing the routing of requests between different _Business Services_, ensuring that the correct workflow is invoked based on the request context. This is similar to the feature provided by KIE Container {PRODUCT_SHORT} (VERSION_80x)

The Data isolation for _Business Services_ connected to a single database" feature ensures that existing process instances remain bound to the process definition from which they were created.

== Automatic execution of {PIM_ADDON} on _Business Service_ startup
In {PRODUCT_SHORT} {VERSION_95x}, the {PIM_ADDON} was run manually by users to execute migration plans after deployment. This meant that if you use Blue/Green deployment pipelines you could not use the {PIM_ADDON} because pipelines terminate the old service version immediately after the new version passes health/readiness probes, and as a consequence there was no window for an operator to trigger the migration externally between the two service versions being live simultaneously.

{PRODUCT_SHORT} {VERSION} enables {PIM_ADDON} to be optionally configured to execute automatically on _Business Service_ startup.

xref:../10-managing-and-monitoring-business-services/migration-with-pim.adoc[Learn more...]

== New Role-based access control for Business Services in production
{PRODUCT_SHORT} {VERSION} provides fine-grained role-based access control (RBAC) at a _Business Service_ level to control access through the Management Console or API. Features can now be restricted by user role, enabling enterprises to enforce read-only or read/write access per capability. Permissions are sourced from the Identity Provider, ensuring centralized governance and compliance.

Using the new Role-based Access Control you are now able to:

- Specify which Management Console pages or actions are visible for specific user profiles depending on their permissions.
- Protect the underlying Business Service REST and GraphQL endpoints by role.
- Utilize your existing role definitions in the OpenID Connect (OIDC) Identity Provider that you are using in your organization (Keycloak, Auth0, Okta, or Azure AD).

The capability is provided through two new add-ons: 

{RBAC_ADDON}:: Exposes user permissions to the Management Console via a `/me` endpoint, and optionally cross-checks permissions against the Business Service's route security. 

BAMOE RBAC Data-Index Add-on:: Enforces role-based access on the Data Index GraphQL endpoint (`/graphql`).
