== Workflow versioning across Business Service deployments
{PRODUCT_SHORT} {VERSION} supports the creation and deployment of a new _Business Service_ that contains a new version of the Process Definition while maintaining the same Process ID. The new Process Definition is uniquely identified with a Version number and the recommended strategy for managing the evolution of a _Business Service_ is **one Business Service, one version**. 

In previous versions of {PRODUCT_SHORT} {VERSION_X} versioning was done by adding an updated Process with a new Process ID. This strategy meant that updating a workflow generated multiple IDs, and client applications had to be updated to use new endpoints (e.g., /hiring to /hiring2). xref:../09-building-and-deploying-business-services/services-deployment.adoc#evolving-deployed-workflows[Learn more...]

The ability to manage multiple _Business Service_ versions with the same Process ID streamlines the migration of Process Instances to an updated Process Definition using the new {PIM_ADDON} functionality of *Remote* migration plans. xref:../10-managing-and-monitoring-business-services/migration-with-pim.adoc#remote-migration-plan[Learn more...]

== Automatic execution of {PIM_ADDON} to migrate _Business Services_ on startup
When deploying a new version of a _Business Service_ containing an updated Process Definition via a CI/CD pipeline there is often no simple way to migrate in-flight Process Instances to the new version. 

To address this {PRODUCT_SHORT} {VERSION} can now automatically trigger the {PIM_ADDON} on Business Service startup using *Installed* migration plans specified in JSON files. This functionality enables you to use your existing CI/CD pipelines without the need for complex modifications. {PIM_ADDON_SHORT} automatically registers *Installed* plans and migrates all matching active Process Instances on deployment of a _Business Service_ containing an updated Process Definition. It uses distributed locking to guarantee exactly-once execution across replicas. xref:../10-managing-and-monitoring-business-services/migration-with-pim.adoc#auto-migration[Learn more...]

== Workflow engine - Data isolation for _Business Services_ connected to a single database

When multiple _Business Services_ are deployed within the Compact Architecture configuration, they may share the same database. In {PRODUCT_SHORT} {VERSION_RM}, you are now able to activate data isolation between services with a single configuration property: `kogito.persistence.data-isolation.enabled=true`. When enabled, each _Business Service_ automatically filters all database queries to return only its own data. The filtering happens at the SQL level and no additional network calls or external services are required. Use this feature to remove any risk of data leakage between services. 

This feature is opt-in and disabled by default, so existing deployments are unaffected until you explicitly enable data isolation through the configuration property. xref:../08-developing-stateful-workflows/database-considerations.adoc#data-isolation-shared-databases[Learn more...]

== New Role-based access control for Business Services in production
{PRODUCT_SHORT} {VERSION} provides fine-grained role-based access control (RBAC) at a _Business Service_ level to control Management Console or Data-Index GraphQL API operations. The functionality is provided through two new add-ons: 

{RBAC_ADDON}:: Exposes user permissions to the Management Console via a `/me` endpoint to specify which pages or actions are visible for specific user profiles. Optionally cross-checks permissions against the Business Service's route security.

BAMOE RBAC Data-Index Add-on:: Enforces role-based access on the underlying Data Index GraphQL endpoint (`/graphql`).

RBAC reuses existing role definitions defined by the OpenID Connect (OIDC) Identity Provider that your organization uses (Keycloak, Auth0, Okta, or Azure AD), ensuring centralized governance and compliance. xref:../09-building-and-deploying-business-services/security.adoc#rbac-config[Learn more...]

== Database password encryption in BAMOE container images
With {PRODUCT_SHORT} {VERSION}, the {DATA_CLEANUP} now offers two new ways to supply database credentials: encrypted (AES-GCM, decrypted by the tool at startup), and Vault (fetched from HashiCorp Vault when the tool starts). The tool decides which mode to use based on environment variables settings and no configuration file changes are needed. xref:../10-managing-and-monitoring-business-services/managing-runtime-data.adoc#password-cred[Learn more...]

== Support for dynamic sub-process invocation

{PRODUCT_SHORT} {VERSION} includes dynamic sub-process calls, that are supported through Call Activities. The `#{variable_name}` syntax in the `calledElement` attribute allows the identifier of the called sub-process to be resolved from a process variable at runtime. This feature was supported by {PRODUCT_SHORT} 8, and the availability of this feature in {VERSION} facilitates migration of BAMOE 8 applications to this version.

xref:../08-developing-stateful-workflows/authoring-workflows.adoc#dynamic-call-activity[Learn more...]
