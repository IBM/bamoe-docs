= Upgrading custom WorkItemHandlers

include::../partials/attributes.adoc[]
include::../styles/images.adoc[]

This guide explains how to migrate custom WorkItemHandlers from BAMOE v8 to BAMOE v9. It outlines the key differences in APIs, registration mechanisms, and execution models, and provides a step-by-step example of implementing and deploying a custom WorkItemHandler in BAMOE v9.

== What Is a Custom Work Item in BAMOE?

In BAMOE, a Work Item represents a task or activity in a process that typically involves external operations, such as calling REST APIs, performing database operations, or consuming SOAP web services. A Custom Work Item Handler (WIH) is a user-defined Java class that implements the logic for executing such tasks. It extends the capabilities of standard BPMN tasks (like Service Tasks) by allowing developers to plug in custom code to meet specific business requirements not covered by built-in functionality.

Custom Tasks can also define visual and runtime properties for the node on the process model, enhancing both modeling and execution flexibility.

== Differences Between BAMOE 8 and 9

=== API and Lifecycle Changes

In BAMOE v8, custom WorkItemHandlers implemented the interface `org.kie.api.runtime.process.WorkItemHandler` and used the methods `+executeWorkItem(...)+` and `+abortWorkItem(...)+`.

In BAMOE v9, these methods are no longer supported. Instead, handlers must extend `org.kie.kogito.process.workitems.impl.DefaultKogitoWorkItemHandler` and override:

* `+activateWorkItemHandler(...)+` -- for executing the task
* `+abortWorkItemHandler(...)+` -- for handling abort scenarios

The new model is based on phases and transitions, which provide more flexibility and better integration with the Kogito runtime.

=== Registration Changes

In v8, handlers were registered using `kie-deployment-descriptor.xml` or `kmodule.xml`.

In v9, handlers must be registered programmatically by extending `org.kie.kogito.process.impl.DefaultWorkItemHandlerConfig`.

Example:

[,Java]
----
@ApplicationScoped
public class CustomWorkItemHandlerConfig extends DefaultWorkItemHandlerConfig {
    {
        register("MyConcatDefinitions", new MyConcatWorkItemHandler());
    }
}
----

=== Annotation Support

The `@Wid` annotation used in BAMOE v8 is no longer supported in BAMOE v9. Instead, Work Item Definitions must be provided as .wid files and placed in either:

* the top-level `global/` directory, or
* the `src/main/resources/` directory, optionally within a Java package structure (e.g., `src/main/resources/com/ibm/`).

== Creating a Custom WorkItemHandler in BAMOE 9

This section provides a step-by-step guide for implementing a custom WorkItemHandler in BAMOE v9, including project setup, handler definition, and integration with a BPMN process.

To get started, create a BAMOE Maven project using the BAMOE Accelerator:

[,sh]
----
git clone https://github.com/IBM/bamoe-canvas-quarkus-accelerator -b 9.2.0-ibm-0004-quarkus-full my-business-service-project
----

In your project's `pom.xml`, add the following dependency to enable the necessary APIs:

[,xml]
----
<dependency>
    <groupId>org.kie.kogito</groupId>
    <artifactId>kogito-api</artifactId>
</dependency>
----

=== Creating .wid Files and Icons

In BAMOE v9, the `@Wid` annotation is no longer supported. Instead, Work Item Definitions must be provided as `.wid` files. These files can be placed in:

* The top-level `global/` directory, or
* The `src/main/resources/` directory, optionally within a Java package structure (e.g., `src/main/resources/com/ibm/`).

Icons for custom tasks can be placed in the same directory as the `.wid` file.

Example `.wid` content:

[,json]
----
[
    [
        "name" : "MyConcatDefinitions",
        "displayName" : "MyConcatDefinitions",
        "category" : "myconcatworkitem",
        "description" : "",
        "defaultHandler": "mvel: new com.ibm.MyConcatWorkItemHandler()",
        "parameters" : [
            "FirstName" : new StringDataType(),
            "LastName" : new StringDataType()
        ],
        "results" : [
            "FullName" : new StringDataType()
        ],
        "icon" : "MyConcatDefinitions.png"
    ]
]
----

NOTE: In some cases, VS Code may not immediately recognize the `.wid` file, causing the custom Work Item to be unavailable in the designer palette. To resolve this, run `git add customtask.wid` to ensure the file is tracked. If the issue persists, try reopening the BAMOE project in a new VS Code workspace.

=== Implement the Custom WorkItemHandler

To implement the custom logic, create a Java class named `MyConcatWorkItemHandler`. This class should extend `org.kie.kogito.process.workitems.impl.DefaultKogitoWorkItemHandler` and override the `+activateWorkItemHandler(...)+` and `+abortWorkItemHandler(...)+` lifecycle methods to define the behavior of your Custom Task.

[,java]
----
import org.kie.kogito.internal.process.workitem.KogitoWorkItem;
import org.kie.kogito.internal.process.workitem.KogitoWorkItemHandler;
import org.kie.kogito.internal.process.workitem.KogitoWorkItemManager;
import org.kie.kogito.internal.process.workitem.WorkItemTransition;
import org.kie.kogito.process.workitems.impl.DefaultKogitoWorkItemHandler;
import org.slf4j.LoggerFactory;

public class MyConcatWorkItemHandler extends DefaultKogitoWorkItemHandler {

    private static final org.slf4j.Logger LOG = LoggerFactory.getLogger(MyConcatWorkItemHandler.class);

    @Override
    public Optional<WorkItemTransition> activateWorkItemHandler(KogitoWorkItemManager manager, KogitoWorkItemHandler handler, KogitoWorkItem workItem, WorkItemTransition transition) {

        for (String parameter : workItem.getParameters().keySet()) {
            LOG.info(parameter + " = " + workItem.getParameters().get(parameter));
 }

        Map<String, Object> results = new HashMap<String, Object>();

        String firstName = (String) workItem.getParameter("FirstName");
        String lastName = (String) workItem.getParameter("LastName");
        String fullName = firstName + " " + lastName;

        results.put("FullName", fullName);

        return Optional.of(handler.completeTransition(workItem.getPhaseStatus(), results));

 }
    @Override
    public Optional<WorkItemTransition> abortWorkItemHandler(KogitoWorkItemManager manager, KogitoWorkItemHandler handler, KogitoWorkItem workItem, WorkItemTransition transition) {
        LOG.info("Aborting work item " + workItem);
        return Optional.of(this.workItemLifeCycle.newTransition("abort", workItem.getPhaseStatus(), workItem.getResults()));
 }
}
----

==== Registering the Custom WorkItemHandler

To use a custom WorkItemHandler in a process instance, it must be registered before the process starts. This registration informs the engine which handler to invoke for a given task.

Register your handler by extending `DefaultWorkItemHandlerConfig`:

[,java]
----
import org.kie.kogito.process.impl.DefaultWorkItemHandlerConfig;
import jakarta.enterprise.context.ApplicationScoped;

@ApplicationScoped
public class CustomWorkItemHandlerConfig extends DefaultWorkItemHandlerConfig {

    {
        register("MyConcatDefinitions", new MyConcatWorkItemHandler());
    }
}
----

=== Build and run

==== Prerequisites

Ensure the following tools are installed and configured:

* Java 17+ installed
* Environment variable JAVA_HOME set accordingly
* Maven 3.9.6+ installed

For native image compilation (optional):

* GraalVM 19.1+ installed
* Environment variable GRAALVM_HOME set accordingly
* Note that GraalVM native image compilation typically requires other packages (glibc-devel, zlib-devel and gcc) to be installed too, please refer to GraalVM installation documentation for more details.

==== Compile and Run in Local Dev Mode

Use Quarkus dev mode to run the application with hot reload support:

[,sh]
----
mvn clean compile quarkus:dev
----

NOTE: Dev mode allows hot reload of business assets like processes, rules, decision tables, and Java code--no need to restart the application.

==== Package and Run in JVM Mode

[,sh]
----
mvn clean package
java -jar target/quarkus-app/quarkus-run.jar
----

On windows

[,sh]
----
mvn clean package
java -jar target\quarkus-app\quarkus-run.jar
----

==== Package and Run using Local Native Image

To compile a native executable, first add the following property to `application.properties`:

----
quarkus.native.auto-service-loader-registration=true
----

Then build the native image:

[,sh]
----
mvn clean package -Pnative
----

Run the generated executable:

[,sh]
----
./target/process-service-rest-call-quarkus-runner
----

=== Submit a Request

To invoke the process, send a POST request to `+http://localhost:8080/CustomTaskDemo+` with the following payload:

[,json]
----
{
  "FirstName": "Alex",
  "LastName": "Tom"

}
----

Example using `curl`:

[,sh]
----
curl -X 'POST' \
 'http://localhost:8080/CustomTaskDemo' \
  -H 'accept: */*' \
 -H 'Content-Type: application/json' \
  -d '{
 "FirstName": "Alex",
 "LastName": "Tom"

}'
----
