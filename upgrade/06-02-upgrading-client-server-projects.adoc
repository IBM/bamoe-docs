= Upgrading client server projects

include::../partials/attributes.adoc[]
include::../styles/images.adoc[]

This guide provides a step-by-step process for upgrading client-server projects from BAMOE v8 to v9, covering key changes in configuration, security, and deployment.
While both versions use standard Maven project structures (e.g., `pom.xml`, `src/main/java`, `src/main/resources`), there are important differences that must be addressed to ensure a successful migration.

== pom.xml

The pom.xml file used in BAMOE v8 is not compatible with BAMOE v9. To create a compatible pom.xml, you can either use a BAMOE Accelerator or manually configure it from scratch.

=== Manual upgrade

If you prefer more control over your Maven configuration, you can manually upgrade your pom.xml by selecting the appropriate dependencies from the official BAMOE Maven repository:

* https://www.ibm.com/docs/en/ibamoe/9.2.x?topic=reference-bamoe-maven-repository-libraries[BAMOE Maven Repository Libraries]

This approach is ideal for advanced users who want to fine-tune their project setup or integrate with existing enterprise build pipelines.

=== Using BAMOE Accelerator

BAMOE Accelerators are project templates with a ready-to-use structure designed to help you quickly get started with a Business Service project. These templates include a preconfigured pom.xml tailored for BAMOE v9.

The easiest way to upgrade your project is to replace your existing v8 pom.xml with the one provided in the BAMOE v9 accelerator, available here:

* https://github.com/IBM/bamoe-canvas-quarkus-accelerator[BAMOE Canvas Quarkus Accelerator (GitHub)].

*NOTE:* Use the `pom.xml` content from a branch corresponding to to your BAMOE v9 version.

BAMOE v9 offers two types of accelerators, depending on the nature of your Business Service project:

* *DMN Accelerator* -- Focused on Decisions and Rules using DMN.
* *Full Accelerator* -- Includes Workflows, Decisions and Rules, suitable for more complex automation scenarios.

Choose the one that best matches your project requirements.

BAMOE Accelerator templates can be used also directly from *BAMOE Canvas*. See https://www.ibm.com/docs/en/ibamoe/9.2.x?topic=canvas-using-accelerators[BAMOE Documentation].

*NOTE:* You can not simply *Apply Accelerator* from the *BAMOE Canvas* to whole BAMOE v8 Business Service project. It would result into invalid project structure. See the link:10-known-limitations.adoc[Known limitations] chapter.

== application.properties [[application-properties]]

The `application.properties` content of BAMOE v8 is not compatible with BAMOE v9.
Below is a summary explaining what properties belongs to v8 and v9.

|===
| Feature | v8 | v9

| `kieserver.*` properties
| ✅ Used
| ❌ Deprecated

| `drools.*` properties
| ✅ Used
| ❌ Deprecated

| `jbpm.*` properties
| ✅ Used
| ❌ Deprecated

| `kogito.*` properties
| ❌ Not available
| ✅ Introduced
|===

Furthermore, the BAMOE v9 `application.properties` content will depend on the used technology.

*NOTE:* Please review https://www.ibm.com/docs/en/ibamoe/9.2.x?topic=notes-supported-environments[BAMOE Supported environments].

There is not one dedicated place that would list all possible configurations of BAMOE v9 `application.properties`.
However a good way to explore the configuration is to search for `application.properties` string in the official https://www.ibm.com/docs/en/ibamoe/9.2.x[BAMOE Documentation].

Similar to `pom.xml` also `application.properties` can be found in BAMOE Accelerators available https://github.com/IBM/bamoe-canvas-quarkus-accelerator[here].

*NOTE:* Use `application.properties` content from a branch corresponding to to your BAMOE v9 version.

== Security configurations

Users and roles in v8 can come from WildFly server (Jboss EAP), LDAP or SSO providers like Keycloak.
However we need to distinguish between securing development environment (Business Central v8 vs. BAMOE Canvas v9) and production environment (KIE Server v8 vs. Quarkus / Spring Boot v9).

BAMOE v9 development environment v9 has no built in mechanism for Authorization and Authentication.
It is a responsibility of users to control who can access their Business Service projects out of BAMOE.

How we secure BAMOE v9 production environment is described in https://www.ibm.com/docs/en/ibamoe/9.2.x?topic=services-securing-business-service-api-endpoints[BAMOE Documentation].

Below we describe few more details how to do production environment security configuration in BAMOE v9.

=== Wildfly/Jboss -> Quarkus security

This approach is intended for development and testing environments
It is not recommended for production because:

* It supports only plain-text and MD5-hashed passwords.
* `.properties` files are limited in flexibility and security.

*NOTE:* Please read more about https://quarkus.io/guides/security-properties[Quarkus security].

To adopt this approach a Maven dependency is required:

[,xml]
----
<dependency>
  <groupId>io.quarkus</groupId>
  <artifactId>quarkus-elytron-security-properties-file</artifactId>
</dependency>
----

==== Embedded Realm example properties

Users and roles are defined directly in the configuration.

[,properties]
----
quarkus.security.users.embedded.plain-text: true or false (default: false)
quarkus.security.users.embedded.algorithm: e.g., digest-md5, digest-sha-256
quarkus.security.users.embedded.users: user-password mappings
quarkus.security.users.embedded.roles: user-role mappings
----

==== File Realm example properties:

Users and roles are defined in external `.properties` files.

[,properties]
----
quarkus.security.users.file.enabled: true or false
quarkus.security.users.file.plain-text: true or false
quarkus.security.users.file.users: path to the users file
quarkus.security.users.file.roles: path to the roles file
----

If not using plain text, passwords must be hashed using:

----
HEX(MD5(username ":" realm ":" password))
----

Using the Quarkus `.properties`-based security configuration can prompt users with a login screen, but it depends on how your application is set up--particularly the HTTP authentication mechanism you configure.

By default, when you secure endpoints using Quarkus and configure users via `.properties` files, Quarkus uses HTTP Basic Authentication unless you specify otherwise.

==== With HTTP Basic Auth:

* The browser shows a native login dialog (not a custom HTML form).
* Users must enter a username and password.
* If credentials are valid (as per your .properties files), access is granted.

[,properties]
----
# default config
quarkus.http.auth.basic=true
----

==== With Form-Based Auth (custom login page):

* You can configure Quarkus to use a custom login form.
* This requires additional setup using `quarkus-elytron-security-web` and configuring a login page, error page, etc.

*NOTE:* Please have a look on https://github.ibm.com/dba/bamoe-examples/tree/main/process-security[BAMOE process-security example] to see complete project structure.

=== Wildfly/Jboss -> Spring Boot security

To adopt this approach a Maven dependency is required:

[,xml]
----
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-security</artifactId>
</dependency>
----

Spring Boot automatically:

* Secures all HTTP endpoints by default.
* Enables HTTP Basic Authentication.
* Creates a default user with a randomly generated password (printed in the console at startup).
* Requires authentication for every request unless explicitly configured otherwise.

When you run the app, you'll see something like:

----
Using generated security password: 8f3b2c1a-xxxx-xxxx-xxxx-xxxxxxxxxxxx
----

You can override this in application.properties:

[,properties]
----
spring.security.user.name=admin
spring.security.user.password=secret
spring.security.user.roles=ADMIN
----

You can define a custom security configuration using a `SecurityFilterChain` bean:

[,java]
----
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public/**").permitAll()
                .anyRequest().authenticated()
            )
            .formLogin(); // Enables form-based login
        return http.build();
    }
}
----

You can secure methods or endpoints using annotations:

[,java]
----
@PreAuthorize("hasRole('ADMIN')")
public void adminOnlyMethod() { ... }

@Secured("ROLE_USER")
public void userMethod() { ... }
----

Unlike the `.properties`-based approach in Quarkus, which is explicitly intended for development and testing, Spring Boot's security setup is robust, extensible, and secure by default. It is fully suitable for production use, provided that best practices are followed.

To begin with, avoid hardcoding credentials in application.properties. Instead, use environment variables or external configuration sources, and consider integrating with a user database or identity provider. For password handling, Spring Security uses BCrypt by default, which is a secure choice. Plain-text passwords should be strictly avoided.

Authentication should be customized to suit your environment. Replace the default in-memory user store with a UserDetailsService backed by a database or LDAP. For modern authentication needs, consider using OAuth2, JWT, or OpenID Connect.

Finally, ensure that your endpoints are properly secured. Use annotations like `@PreAuthorize`, `@Secured`, or configure access rules through a `SecurityFilterChain`. Additionally, enable HTTPS and CSRF protection as needed to safeguard your application in production environments.

=== LDAP

Quarkus provides built-in support for LDAP-based authentication through the quarkus-elytron-security-ldap extension. This allows you to authenticate users against an LDAP directory and map their roles for access control.

To enable LDAP authentication:

Add the required dependencies to your `pom.xml`:

[,xml]
----
<dependency>
  <groupId>io.quarkus</groupId>
  <artifactId>quarkus-resteasy</artifactId>
</dependency>
<dependency>
  <groupId>io.quarkus</groupId>
  <artifactId>quarkus-elytron-security-ldap</artifactId>
</dependency>
----

Configure LDAP settings in `application.properties`:

[,properties]
----
quarkus.security.ldap.enabled=true
quarkus.security.ldap.dir-context.url=ldap://localhost:389
quarkus.security.ldap.dir-context.principal=uid=admin,ou=system
quarkus.security.ldap.dir-context.password=admin

quarkus.security.ldap.identity-mapping.rdn-identifier=uid
quarkus.security.ldap.identity-mapping.search-base=ou=users,dc=example,dc=com
quarkus.security.ldap.identity-mapping.attribute-mappings=cn:roles
quarkus.security.ldap.identity-mapping.search-recursive=true
----

Secure your endpoints using role-based annotations:

*src/main/java/org/acme/security/ldap/HelloResource.java*

[,java]
----
package org.acme.security.ldap;

import jakarta.annotation.security.RolesAllowed;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;

@Path("/api")
public class HelloResource {

    @GET
    @Path("/public")
    public String publicEndpoint() {
        return "This is a public endpoint.";
    }

    @RolesAllowed("standardRole")
    @GET
    @Path("/users/me")
    public String userEndpoint() {
        return "Welcome, user!";
    }

    @RolesAllowed("adminRole")
    @GET
    @Path("/admin")
    public String adminEndpoint() {
        return "Welcome, admin!";
    }
}
----

For more details, see the https://quarkus.io/guides/security-ldap[Quarkus LDAP Security Guide].

=== Wildfly/Jboss SSO to Keycloak OIDC

In BAMOE v8, security was often configured using WildFly's built-in mechanisms or JBoss SSO. In BAMOE v9, these are replaced by modern, standards-based authentication using Keycloak and OpenID Connect (OIDC).

Both Quarkus and Spring Boot offer first-class support for OIDC, allowing you to secure services using bearer tokens issued by Keycloak or any other OIDC-compliant identity provider. This approach is more flexible, cloud-native, and better suited for containerized and microservice-based deployments.

With BAMOE v9, the platform includes the `process-security` example, which demonstrates a full Quarkus application integrated with Keycloak. Additionally, the https://quarkus.io/guides/security-oidc-bearer-token-authentication[Quarkus OIDC Bearer Token Authentication Guide] provides detailed instructions for setting up OIDC in a Quarkus application.

This modern security model eliminates the need for WildFly-specific configurations and aligns with BAMOE v9's cloud-native architecture.

== How do you know it worked?

We need our upgraded BAMOE v9 project to be up and running.
To do it we have two options described below.

=== The quarkus dev:mode

The upgraded BAMOE v9 project is a Maven Quarkus project that we can build and start locally as `mvn clean package` `mvn clen quarkus:dev`.
The procedure is described also in getting started with business rule microservice https://www.ibm.com/docs/en/ibamoe/9.2.x?topic=started-rule-service-in-15-minutes[BAMOE Documentation].

Once the dev mode is up and running we should be able to see available Rest endpoints using the address: `+http://localhost:8080/q/swagger-ui/#/+`, however your `application.properties` needs to contain:

[,properties]
----
quarkus.swagger-ui.always-include=true
----

=== Deployment to OpenShift

Is described in getting started with deploying to OpenShift https://www.ibm.com/docs/en/ibamoe/9.2.x?topic=gs-deploying-your-first-business-service-openshift-using-quarkus[BAMOE Documentation].

Once the OpenShift deployment is up and running we should be able to see available Rest endpoints using the address: `[OpenShift deployment endpoint]/q/swagger-ui/#/`, however your `application.properties` needs to contain:

[,properties]
----
quarkus.swagger-ui.always-include=true
----
