= Upgrading from 9.3.x
include::../partials/attributes.adoc[]
include::../styles/images.adoc[]

This section describes the steps you must take to upgrade your {PRODUCT_SHORT} installation and _Business Services_ projects developed in version {VERSION_93X}. 

See the following docs if you are upgrading from a version prior to this:

* xref:upgrade-overview.adoc[Upgrading from a previous version of {PRODUCT_SHORT}]

This guide will walk you through upgrading your:

* {PRODUCT_SHORT} Dev environment with {MVN_REPO}, {CANVAS}, and {DEV_TOOLS}

* _Business Service(s)_ project(s)

* {PRODUCT_SHORT} Runtime environment with {MANAGEMENT_CONSOLE}, {MCP_SERVER} and upgraded versions of your _Business Services_

== Step 1: Download product archives

Start by downloading the product archives from {PRODUCT_PASSPORT_ADVANTAGE_LINK}[IBM Passport Advantage], or via the {DEV_PROGRAM_PAGE_LINK}[IBM Business Automation Manager Open Editions Developer Program]. 

== Step 2: Upgrade your {PRODUCT_SHORT} Dev environment

When you upgrade your {PRODUCT_SHORT} Dev environment in {VERSION}, the individual component deliverables have been replaced by two new Helm charts to facilitate the installation and license tracking of {PRODUCT_SHORT} components in your selected offering, DMOE or PMOE. They include the product specific licensing annotations, removing the need for manual intervention:

The Dev helm charts include the following component Containers:

* {CANVAS}
* {EXT_SERVICES}
* {CORS_PROXY}
* {MVN_REPO}

=== Upgrade {CANVAS} and {MVN_REPO}
It is recommended that you use the https://docs.openshift.com/container-platform/4.19/applications/deployments/route-based-deployment-strategies.html#deployments-blue-green_route-based-deployment-strategies[blue-green deployment strategy] for Maven artifacts to be available for both your current version and {PRODUCT_SHORT} version {VERSION_93X}.

Follow the steps in xref:../installation/development-environment.adoc[Installing → Dev Environment Helm chart] to install the new {MVN_REPO} and {CANVAS} versions.

If you decide to uninstall the previous individual containers and replace with the Dev environment Helm chart, the {VERSION} version of {CANVAS} is a drop in replacement for the {VERSION_93X} version. The projects you saved to your browser before the upgrade can simply be opened after installing the new version. 

You can import projects into the newly installed version (see xref:../tools/importing-existing-projects.adoc[{CANVAS} → Importing existing projects]) as long as the DNS domains between installations are different. If the DNS domains between installations are the same, your imported projects automatically show up in the new installation when you open it in your browser.

[NOTE]
====
If you have customized your previous {CANVAS} installation, remember to apply the same environment variables to the new installation. The same applies for customized container images for {CANVAS} Dev Deployments.
====

=== Upgrade {DEV_TOOLS}
{DEV_TOOLS} versions are managed by the Extension update mechanism in VS Code. You can set automatic update or manage it manually when notified. Because of version differences in the models supported by the BPMN, DMN, and Test Scenario editors it is recommended to choose when you upgrade to avoid issues when running models in services that have not been upgraded when the tools are upgraded. See xref:../tools/developer-tools-for-vscode.adoc[{DEV_TOOLS}].

== Step 3: Upgrade your _Business Service(s)_ project(s)

_Business Service(s)_ project(s) can be upgraded by changing their Maven dependencies and configuration files.  

The following tools are required to upgrade your _Business Service_ projects to {PRODUCT_SHORT} version {VERSION_931}:

- https://openjdk.org[JDK 21] is installed.
- https://maven.apache.org[Apache Maven 3.9.11+] is installed.
- https://code.visualstudio.com/download[Visual Studio Code IDE] latest version installed.
- Upgraded {PRODUCT_SHORT} Dev environment with {MVN_REPO} @ {IMAGE_VERSION}

Once your {PRODUCT_SHORT} Dev environment is upgraded, it is straightforward to upgrade your _Business Service(s)_ project(s) on {PRODUCT_SHORT} {VERSION_93X} to {PRODUCT_SHORT} version {VERSION}.

The project structure is not changed, updates only need to be made to the versions, names of some dependencies and files.

[start=1]
. Upgrade the BAMOE BOM in the project POM file to {BOM_VERSION}:
+
[source,xml,subs="+attributes"]
----
<dependency>
  <groupId>com.ibm.bamoe</groupId>
  <artifactId>bamoe-bom</artifactId>
  <version>{BOM_VERSION}</version>
  <type>pom</type>
  <scope>import</scope>
</dependency>
----

Due to the update to Quarkus and Spring Boot versions that {PRODUCT_SHORT} {VERSION} supports, a number of frameworks have been updated which may impact your _Business Services_ built with {VERSION_93X}. For more information see xref:#Quarkus-Spring-updates[Main Quarkus and Spring Boot Framework changes] and the Quarkus (https://github.com/quarkusio/quarkus/wiki/Migration-Guide-3.27[Quarkus 3.27 LTS migration guide]) and Spring Boot documentation (https://docs.spring.io/spring-boot/upgrading.html[Upgrading Spring Boot]).

== Step 4: Verify the upgrade of your _Business Service(s)_ project(s)

To verify that your upgrade is successful, rebuild the project using Maven's standard command or any other customized build command you might have in your project.

[source,console]
----
mvn clean package
----

You will get Maven streaming text with the message `Build Success` at the end if your upgrade was successful. 

You can now continue developing your _Business Service_ project on {PRODUCT_SHORT} version {VERSION}.

== Step 5: Upgrade your {PRODUCT_SHORT} Runtime environment

After upgrading your _Business Services_ source code (Step 3), you need to upgrade the components in your Runtime environment. 

The {MANAGEMENT_CONSOLE} and {MCP_SERVER} component containers are now available in the Runtime Helm charts for your selected offering (DMOE or PMOE). They include the product specific licensing annotations, removing the need for manual intervention.

Install new versions of {MANAGEMENT_CONSOLE} and {MCP_SERVER}, by following the steps in xref:../installation/runtime-environment.adoc[Installing → Runtime Environment Helm chart].

If you have stateful workflows in your _Business Services_ you will need to complete step 6 to update your database. If you only have DMN and DRL in your _Business Services_ you can now deploy your upgraded _Business Services_.

[#migrate-stateful-workflow-db]
== Step 6: Upgrade your stateful Workflow database(s)

If you have _Business Services_ that run stateful workflows in your system you will upgrade your runtime database using the database migration scripts included in the `bamoe-{VERSION}-db-utils.zip` archive.

The archive provides scripts named `from--$PREVIOUS_RELEASE--to--$CURRENT_RELEASE.sql` for each subsystem in a _Business Service_ that uses the Compact Architecture (Data-Index, Data-Audit, Embedded Jobs Service, User Tasks, and Runtime Persistence).

You must upgrade your _Business Services_ and your database(s) together. 

To upgrade safely:

. Back up your database

. Test the migration in a staging environment

. Schedule downtime if you are updating a production database

. Apply the scripts sequentially for each subsystem 

. Verify that all services function correctly after the upgrade

Avoid using KIE Flyway for automatic database schema migration in production environments. Instead, apply the scripts manually to maintain control and reduce the risk of issues.

For more information, see xref:../building-deploying/services-deployment.adoc#production-database-creation[Creating your database schema for stateful Workflows based on BAMOE Installation DDL scripts] and xref:../workflow/overview.html[Overview of stateful Workflows with Compact Architecture].

Once you have installed your Runtime environment and updated the database for any stateful workflows in your system, you can follow the standard guidance on how to deploy upgraded versions of your _Business Services_ (see xref:../building-deploying/services-build.adoc[Building Business Services executables] and xref:../building-deploying/services-deployment.adoc[Deploying Business Services]).

[#Quarkus-Spring-updates]
== Breaking changes due to Quarkus and Spring Boot Framework updates

{PRODUCT_SHORT} {VERSION_94} updates the core frameworks that power _Business Services_. The most impactful change is the Hibernate ORM 6.x to 7.1 upgrade, which introduces breaking API changes that require code modifications. The following table lists and categorizes these changes. 

|===
| Component | {VERSION_931} | {VERSION_94} | Change Type | Impact

| Quarkus | 3.20.3 | 3.27.2 | Minor | HIGH

| Spring Boot | 3.4.x | 3.5.10 | Minor | MEDIUM

| Spring Framework | 6.1.x | 6.2.15 | Minor | MEDIUM

| Hibernate ORM | 6.2.13 | 7.1.14 | Major | CRITICAL

| Kafka Client | 3.6.x | 4.0.0 | Major | MEDIUM

| Fabric8 K8s Client | 7.1.0 | 7.3.1 | Minor | MEDIUM

| AsyncAPI | 2.x (jar 0.30.0) | 3.x (jar 1.0.5) | Major | HIGH

| Jackson | 2.17.x | 2.19.2 / 2.21.1 | Minor | LOW

| GraphQL Java | 22.0 | 24.3 | Minor | MEDIUM

| Netty | 4.1.x | 4.1.131.Final | Minor | LOW

| Vert.x | 4.5.x | 4.5.24 | Patch | LOW

| JUnit Jupiter | 5.10.x | 5.12.2 / 5.13.4 | Minor | LOW

|===


=== Hibernate ORM 6.x → 7.1

Hibernate 7.1 is a major version upgrade with breaking API changes, and represents the highest-impact change in this release. In addition, Hibernate ORM 7.1.x license changed from LGPL to Apache License 2.0, removing previous restrictions on Apache-licensed distributions.

|===
| *Change* | *Before (Hibernate 6.x)*| *After (Hibernate 7.1)*

| `UserType` interface | No generic param | Requires generic type (e.g., `UserType<JsonNode>`)

| `nullSafeGet` signature | `String[] names` param | `int position` param

| SQL type declaration | Not required | Must implement `getSqlType()` using `SqlTypes` constants

| Custom SQL functions | Simple constructor | Must implement `render()` with `SqlAppender`

| Boolean type reference | `StandardBasicTypes.BOOLEAN` | `BasicTypeReference<>(SqlTypes.BOOLEAN)`

| Native query return types | Returns `java.util.Date` | Returns `java.time.OffsetDateTime`

| `@Temporal` annotations | Required for date fields | Not needed for `OffsetDateTime` fields (handled natively)

| EntityManager dependency | `hibernate-entitymanager` | `hibernate-core` (entitymanager merged in)
|===

The following new configuration properties are available for Hibernate in Quarkus:

[source, json]
----
quarkus.hibernate-orm.physical-naming-strategy=org.hibernate.boot.model.naming.CamelCaseToUnderscoresNamingStrategy
quarkus.hibernate-orm.jdbc.timezone=UTC
quarkus.hibernate-orm.flush.mode=always
----

For Spring Boot there is a known compatibility issue between Hibernate 7 and Spring ORM 6.2 around `EntityManagerFactory` initialization. A `BeanPostProcessor` workaround may be needed — see the Hibernate ORM 7.x Breaking Changes Analysis design document.

=== Kafka 3.6.x → 4.0.0
A major version change with limited impact on _Business Services_ built with {PRODUCT_SHORT}.

Test code::
`MockProducer` default constructor was removed, use `new MockProducer<>(true, null, null)` instead. 

=== AsyncAPI 2.x → 3.x
The AsyncAPI specification and Java library had a major version upgrade, which affects the spec files and Java code referencing AsyncAPI models.

Spec files must be converted: 

[source, console]
----
asyncapi convert asyncapi-2.yaml --target-version=3.0.0 --output=asyncapi-3.yaml
----

The Java package `com.asyncapi.v2._6_0` has been renamed to `com.asyncapi.v3._0_0`.

`ChannelItem` renamed to `Channel` and you will need to use `channel.getAddress()` instead of channel name as the key.

Operations now use explicit `OperationAction` (`SEND` or `RECEIVE`).

Internal {PRODUCT_SHORT} integration migrated to `io.quarkiverse.asyncapi.config.AsyncAPISupplier` and `MapAsyncAPIRegistry`.


=== Fabric8 Kubernetes Client 7.1.0 → 7.3.1
This represents a minor update with no breaking changes for most use cases, as described:

* CDI injection (@Inject KubernetesClient) works the same way
* Additional support for both Kubernetes and OpenShift resource discovery
* Test annotation changed: `@WithKubernetesTestServer` replaced by `@QuarkusTestResource(KubernetesMockServerTestResource.class)`

=== GraphQL Java 22.0 → 24.3 (Spring Boot only)
Most APIs (`DataFetcher`, `RuntimeWiring`) remain compatible. There is one configuration change for Spring Boot:

[source, properties]
----
spring.autoconfigure.exclude=org.springframework.boot.actuate.autoconfigure.observation.graphql.GraphQlObservationAutoConfiguration

=== Quarkus Configuration Mechanism
Quarkus 3.27 continues the shift from @ConfigGroup annotations to @ConfigMapping interfaces. This was a prerequisite change applied before the main upgrade. If you have custom Quarkus extensions, review your configuration classes.

----

=== Known Issues

Hibernate 7 + Spring ORM 6.2 EntityManagerFactory initialization issue — workaround via BeanPostProcessor


== Common Errors After Upgrade

|===
| *Error message* | *Cause* | *Fix*

| ClassNotFoundException: com.asyncapi.v2...ChannelItem | AsyncAPI 3.x package rename | Update imports to com.asyncapi.v3._0_0.model.*

| OIDC proxy errors or secure runtime service fails to start | quarkus-oidc-proxy upgraded from 0.2.2 to 0.3.2 | Update quarkus-oidc-proxy version to 0.3.2 in your pom.xml
|===
