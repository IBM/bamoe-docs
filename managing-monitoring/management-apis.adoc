= The Management APIs
include::../partials/attributes.adoc[]

In {PRODUCT_SHORT}, Management APIs are provided to interact with Process Definitions and active Process and Task Instances. These APIs enable you to obtain metadata information about Process Definitions, as well as provide management endpoints for active Process or Task Instances.

[#management-api]
== Process Management API
The `kie-addons-quarkus-process-management` is an extension for {PRODUCT_SHORT} that enables Process Management features for _Business Services_ with workflow(s) in a Quarkus-based microservice architecture.

[source,xml]
----
<dependency>
  <groupId>org.kie</groupId>
  <artifactId>kie-addons-quarkus-process-management</artifactId>
</dependency>
----

With the Process Management API endpoints, you can operate with the following Entities:

* Processes (GET, POST, DELETE)
* ProcessInstance (GET)
* Node (GET, POST, DELETE)
* ProcessError (GET)
* WorkItem (GET)

The following sections describe the Process Management API in detail.

== Task Management API
The `jbpm-addons-quarkus-task-management` and `jbpm-addons-springboot-task-management` are extensions for {PRODUCT_SHORT} that enable Task Management features for _Business Services_ with workflows in a Quarkus-based or Spring Boot based microservice architecture respectively (see )

To enable the Task Management API in Quarkus-based services include this dependency:

[source, xml]
----
<dependency>
    <groupId>org.jbpm</groupId>
    <artifactId>jbpm-addons-quarkus-task-management</artifactId>
</dependency>
----

To enable the Task Management API in Spring Boot-based services include this dependency:

[source, xml]
----
<dependency>
    <groupId>org.jbpm</groupId>
    <artifactId>jbpm-addons-springboot-task-management</artifactId>
</dependency>
----

With the Task Management API endpoint, it’s possible to operate with the following Entity:

== Callback Jobs Service Management API

In {PRODUCT_SHORT}, the Callback Jobs Service Management API endpoints are used to manage callbacks into the runtime engine from an external job service. These callbacks allow external systems, such as the job service, to trigger the execution of a TriggerJobCommand. If successful, the process instance linked to this command gets signalled and resumes its execution. This API is provided by the following extension:

[source,xml]
----
<dependency>
  <groupId>org.kie</groupId>
  <artifactId>kogito-addons-quarkus-jobs-management</artifactId>
</dependency>
----

NOTE: This API endpoint is not primarily intended for manual invocation.

////
===  /management/jobs/{processId}/instances/{processInstanceId}/timers/{timerId}

[cols="1,1a"]
|===
|*Type* |POST

|*Description* |It triggers the job for the given process and process instance at the specified timer Id

|*Inputs* |
* processId : String (PathParameter)
* processInstanceId : String (PathParameter)
* timerId : String (PathParameter)
* limit : int (QueryParameter) - (Default limit value will be 0)
* payload : String passed in as the request body it includes the correlation id and job id


|*Output* a| * Returns the OK response if the job triggered successfully.

* A _BAD REQUEST_ error is returned if processId or processInstanceId is missing in the request.
* A _NOT FOUND_ error is returned if processId or processInstanceId is not found.
*A _BAD REQUEST_ error is returned if payload  is missing in the request.

|*Example* |curl -X 'POST'
'http://localhost:8080/management/jobs/{processId}/instances/{processInstanceId}/timers/1?limit=0'
-H 'accept: */*'
-H 'Content-Type: application/json'
-d '"string"'

|===

== Process Svg Resource API

In {PRODUCT_SHORT}, the Process Svg Resource API endpoints can be used to obtain a graphical representation of a process in SVG format. There are two variants of SVGs, a static one for the Process Definition itself, as well as a dynamic one for an active process instance which also contains information about the process execution. This API is provided by following extension:

[source,xml]
----
<dependency>
  <groupId>org.kie</groupId>
  <artifactId>kie-addons-quarkus-process-svg</artifactId>
</dependency>
----

===  /svg/processes/{processId}

[cols="1,1a"]
|===

[#process-instance-migration-addon]
== Process Instance Migration (PIM) APIs

NOTE: This feature is available from version {VERSION_931}.

To enable the {PIM_ADDON_SHORT} to manage the migration of in-flight Process Instances to updated and new Process Definitions in Quarkus-based _Business Services_, add the following dependency:

[source,xml]
----
<dependency>
  <groupId>com.ibm.bamoe</groupId>
  <artifactId>bamoe-addons-quarkus-pim</artifactId>
</dependency>
----

In a Spring Boot based _Business Services_ add the following dependency:

[source,xml]
----
<dependency>
  <groupId>com.ibm.bamoe</groupId>
  <artifactId>bamoe-addons-spring-boot-pim</artifactId>
</dependency>
----

The Process Instance (PIM) Add-on exposes a set of REST endpoints that enable you to:

* manage the different migration plans uploaded to PIM
* run process instance migrations with a given plan

image::runtime-services-modeling/pim-swagger.png[Swagger UI showing {PRODUCT_SHORT} PIM Add-on]

===  /pim/plan

[cols="1,1a"]
|===
|*Type* |POST

|*Description* |Used to create a new migration plan to define how to migrate process instances from one process definition version (source) to another process definition version (target)

|*Inputs* a|
* sourceProcessId: String (ID of the process whose instances will be migrated)
* sourceProcessVersion: String (version of the process whose instances will be migrated)
* targetProcessId: String (ID of the process which the instances will be migrated to)
* targetProcessVersion: String (version of the process which the instances will be migrated to)
* nodeMapping: List (contains the mapping of nodes between both processes. Each mapping should contain a “sourceId” and “targetId” defining the node ID in the process BPMN definition respectively.)

|*Output* a| Returns a summary with the results of the operation, including:

* status: http status code of the response
* message: message confirming plan creation or not
* data: JSON object containing the detailed information about the plan creation. Fields it can contain:
** plan: field containing the details of the created migration plan, only be present if the operation was successfully. Among other information related to the plan (source process, target process, mappings…) it contains important information like
*** id: unique identifier of the plan, this id should be used when triggering a migration
*** updatedAt: date when it was created
** validation: contains the detail of the plan validation
*** result: PASSED / FAILED
*** errors: Collection of errors in the node mappings that caused the validation to fail
*** warnings: Collection of warnings in the node mappings to make the user aware that, although the plan is functional, there are unusual situations in the mappings (nodes missing in target process, wrong mappings…). 

|*Example* a|

curl -X 'POST' \
  'http://localhost:8080/pim/plan' \
  -H 'accept: */*' \

  "sourceProcessId": "hiring",
  "sourceProcessVersion": "1.0",
  "targetProcessId": "hiring2",
  "targetProcessVersion": "2.0",
  "nodeMapping": [
    {"sourceId": "_B8C4F63C-81AD-4291-9C1B-84967277EEF6", "targetId": "_CBB6BF5D-21DA-43D2-A20B-C361694AF7AE"},

===  /pim/migration

This endpoint will execute the migration of the active Process Instances of a source process to a target process using the specified migration plan.  This endpoint also enables you to do a full migration (migrate all Process Instances) or migrate only a limited set of Process Instances (bulk migrate) by passing the process instances IDs in the request.

To avoid issues on the database when performing a migration of a set of instances PIM limits the number of IDs that can be sent to the `POST /pim/migration` depending on the Database vendor. The limits are:

* H2 → 50000 ids
* PostgreSQL → 50000 ids
* Oracle → 1000 ids
* MS SQL Server → 2000 ids

NOTE: This endpoint may require a varying amount of time to execute depending on the amount of processes instances to migrate, active tasks, jobs, and also the subsystems installed in the _Business Service_ (Data-Index, User Tasks, Storage). It is important to configure the application accordingly to avoid timeouts or issues during execution.

[cols="1,1a"]
|===
|*Type* |POST

|*Description* |Executes the migration of the active Process Instances of a source process to a target process using the specified migration plan..

|*Inputs* a|
The payload should be a JSON object containing the following fields:

* planId: String (ID of the plan to use, the plan defines the source / target process to migrate and the node mapping between processes)
* processInstanceIds: List (optional list containing the IDs of process instances to be migrated, if not provided all active process instances will be migrated) 

|*Output* a| Returns a JSON object listing details of the execution of the migration plan, including:

* migrationId: String (unique ID for the migration)
* planId: String (ID of the plan used on the migration)
* migratedProcessInstancesCount: int (number of Process Instances migrated)
* skippedProcessInstanceIds: int (number of Process Instances that were not migrated, because the IDs provided in the processInstanceIds request payload did not exist or were not an instance of the source process)

|*Example* a|

curl -X 'POST' \
  'http://localhost:8080/pim/migration' \
  -H 'accept: */*' \
  -H 'Content-Type: application/json' \
  -d '{
  "planId": "7c9b7673-d5da-4ad3-aab9-214ca9e72823"
}'

|===
