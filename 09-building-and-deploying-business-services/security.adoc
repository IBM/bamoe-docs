= Securing _Business Services_
include::../_partials/attributes.adoc[]
include::../_styles/images.adoc[]

_Business Services_ on {PRODUCT_SHORT} rely on Quarkus or Spring Boot to configure authentication and authorization, and will query their provided security-related data for information about who the authenticated user is, performing a request and the permissions (roles/groups) they have. This applies particularly to the stateful Workflows subsystem for User Tasks.

After configuring your _Business Service_ to integrate its security layer, you can rely on an external Identity Providers (IdPs) such as Keycloak or Microsoft Entra ID as your project’s Identity and Access Management Solution.

{MANAGEMENT_CONSOLE} can connect to secured _Business Services_ if they expose enough information about their configured Identity Provider. See xref:#mgmt-console-oidc-proxy[Allowing {MANAGEMENT_CONSOLE} to connect to live _Business Services_] for more details. You can also set up a full Role-based access control using the functionality provided in the {RBAC_ADDON} functionality which configures access to Business Services in the Management Console and through the Data Audit GraphQL API (see xref:#rbac-config[Configuring RBAC for _Business Services_ at runtime]). 

== Authentication 
_Business Services_ on {PRODUCT_SHORT} rely on Quarkus or Spring Boot to configure authentication and will query their provided security-related data to identify and authenticate a user. 

[#authentication-quarkus]
=== Quarkus
Quarkus supports the Bearer token authentication mechanism through the Quarkus OpenID Connect (OIDC) extension, based on the https://openid.net/developers/how-connect-works/[OpenID Connect] protocol. You can learn how to set up the authorization layer in Quarkus in this https://quarkus.io/version/3.20/guides/security-oidc-bearer-token-authentication[guide].

The first step is to configure the Quarkus OpenID Connect (OIDC) extension by setting the properties in the `src/main/resources/application.properties` file. 

The list of properties required to setup your project may change based on your security needs, Identity and Access Management Solution, see the example configuration below:

[source]
----
quarkus.oidc.enabled=true
quarkus.oidc.tenant-enabled=true
quarkus.oidc.auth-server-url=http://localhost:8280/auth/realms/kogito
quarkus.oidc.client-id=kogito-service
quarkus.oidc.credentials.secret=secret
----

The following table describes in detail the properties shown in the example, which are a subset of all properties available, see https://quarkus.io/version/3.20/guides/security-oidc-configuration-properties-reference[OIDC configuration property reference] for more information.

[%autowidth]

|quarkus.oidc.enabled | It enables the OIDC extension
 | Boolean | true
|quarkus.oidc.tenant-enabled | It enables the tenant configuration

[#authentication-spring-boot]
=== Spring Boot

Spring Boot supports endpoint protection using OAuth 2.0 Bearer tokens, based on the https://openid.net/developers/how-connect-works/[OpenID Connect] protocol. You can find more information about the Spring Boot OAuth 2.0 Resource Server in the https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/index.html[Spring Documentation].

To use this functionality in a _Business Services_ on {PRODUCT_SHORT}, add the required dependencies to the `<dependencyManagement>` section of your project POM: 

* `org.springframework.boot:spring-boot-starter-security`
* `org.springframework.boot:spring-boot-starter-oauth2-resource-server`

In addition, you will need to configure Spring Security to secure the application with OAuth2. To enable support for bearer tokens based on JSON Web Token (JWT) format, add the following configuration property to your application properties file:

[source]
----
spring.security.oauth2.resourceserver.jwt.issuer-uri=http://127.0.0.1:8180/realms/kie
----

Additional configuration settings can be applied through the Spring Boot `SecurityFilterChain` bean.

== Authorization 
Once a user is authenticated the authorization layer uses that identity (and its associated roles/groups) to decide on the access the user has to _Business Service_ endpoints. If you also configure the {RBAC_ADDON} with permissions for each authenticated role, it is possible to filter the functionality available in {MANAGEMENT_CONSOLE} as well as the operations available through the Data Audit GraphQL API (see xref:#rbac-config[Configuring RBAC for _Business Services_ at runtime]). 

[#authorization-quarkus]
=== Quarkus
Quarkus incorporates a pluggable web security layer. When security is active, the system performs a permission check on all HTTP requests to determine if they should proceed. For more information, see https://quarkus.io/version/3.20/guides/security-authorize-web-endpoints-reference[Authorization of web endpoints] in the official Quarkus guide. See an example configuration below:

[source]
----
quarkus.http.auth.permission.authenticated.paths=/*
quarkus.http.auth.permission.authenticated.policy=authenticated
quarkus.http.auth.permission.public.paths=/q/*,/docs/*,/oidc/info
quarkus.http.auth.permission.public.policy=permit
----

Properties are pluggable based on how many permission rules you want to define for your application.

In the following example, two permissions are defined:

authenticated:: Used for REST endpoints that requires an Authorization.
public:: Used for publicly accessible REST endpoints.

You can find a detailed explanation on permissions and the properties to add to your `application.properties` file in the Quarkus https://quarkus.io/version/3.8/guides/security-authorize-web-endpoints-reference[guide] 

The available properties can be configured for all user-defined permission rules. For example, the `quarkus.http.auth.permission."permissions".policy` property with the specified permissions can have two properties, see following table:

[%autowidth]

|Property | Description | Type 

|quarkus.http.auth.permission."permissions".paths
_e.g.,
quarkus.http.auth.permission.authenticated.paths
quarkus.http.auth.permission.public.paths_

 | The paths that this permission check applies to. If the path ends in /*
then this is treated as a path prefix, otherwise it is treated as an exact
match.
 | List of URI

 |quarkus.http.auth.permission."permissions".policy
_e.g.,
quarkus.http.auth.permission.authenticated.policy

[#authorization-spring-boot]
=== Spring Boot
With Spring Security enabled, you gain fine-grained control over the authorization rules using the `AuthorizationFilter` of the Spring Security Filter Chain. 

The following code snippet shows a sample `AuthorizationFilter` configuration. It enforces authentication for all endpoints, except the `/q/oidc/.well-known/openid-configuration` endpoint which can be accessed unauthenticated. In this sample setup, no specific roles are required to enforce authorization.

[source,java]
----
      .authorizeHttpRequests(auth -> auth
              .requestMatchers("/q/oidc/.well-known/openid-configuration").permitAll()
              .anyRequest().authenticated())
----

You can find more information on this topic and available configuration options in the https://docs.spring.io/spring-security/reference/servlet/authorization/authorize-http-requests.html[Spring Documentation].

[#authentication-usertask-api]
== Authentication in User Task API endpoints
The xref:../08-developing-stateful-workflows/user-tasks.adoc[User Task API] integrates seamlessly with the Authentication and Authorization mechanisms of Quarkus, with the option to receive `user` and `groups` as QueryParameters. For this integration to happen, the following properties should be set in the `application.properties` file of your _Business Service_ project:

[cols="1,1,1,1"]
|===
|*Property* |*Description* |*Type* |*Default* 

|`kogito.security.auth.enabled` | It globally enables the entire application using the Security Context when resolving the current User Identity |Boolean |false 

|`kogito.security.auth.impersonation.allowed-for-roles` | `groupName1,groupName2,...`
Used to specify a list of roles or groups, authorized for identity impersonation when resolving the actual User Identity (comma-separated). Every group defined in this property will act as a superuser, giving all the members part of that group the rights to impersonate any other user. This feature is very useful to change a User Task status assigned to an unavailable user. |String |"" empty string

|===

If `kogito.security.auth.enabled=true` is absent, `kogito.security.auth.impersonation.allowed-for-roles` has no effect and any authenticated user can read another user's tasks through `GET /usertasks/instance?user=<other-user>`. This applies to both Quarkus and Spring Boot.

=== JWT claim mapping for Spring Boot

When `kogito.security.auth.enabled=true` is set, the {PRODUCT_SHORT} `SpringIdentityProvider` reads the authenticated user's name and roles from the Spring Security context to filter User Tasks. For this to work correctly with JWT-based authentication, the JWT claims must be mapped to the right values before `SpringIdentityProvider` is called.

For Identity Providers that store roles in a flat top-level claim, use the following Spring Boot application properties:

[source,properties]
----
spring.security.oauth2.resourceserver.jwt.principal-claim-name=<username-claim>
spring.security.oauth2.resourceserver.jwt.authorities-claim-name=<roles-claim>
spring.security.oauth2.resourceserver.jwt.authority-prefix=<prefix>
----

NOTE: For Microsoft Entra ID roles are in the `roles` claim, and for OKTA roles are in the `groups` claim.

For Identity Providers that store roles in a nested path, provide a custom `JwtAuthenticationConverter`.

For example, in Keycloak roles are stored in the nested `realm_access.roles` claim. Spring Boot 4.0.x has no property-based support for nested claim paths, so a `JwtAuthenticationConverter` bean must be configured in the application's security configuration class as shown below:

[source,java]
----
@Bean
public JwtAuthenticationConverter keycloakJwtAuthenticationConverter() {
    JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
    // Use preferred_username as the principal name
    converter.setPrincipalClaimName("preferred_username");
    // Extract roles from Keycloak's nested realm_access.roles claim
    converter.setJwtGrantedAuthoritiesConverter(MySecurityConfig::extractRealmRoles);
    return converter;
}

@SuppressWarnings("unchecked")
private static Collection<GrantedAuthority> extractRealmRoles(Jwt jwt) {
    Map<String, Object> realmAccess = jwt.getClaim("realm_access");
    if (realmAccess == null) {
        return Collections.emptyList();
    }
    List<String> roles = (List<String>) realmAccess.getOrDefault("roles", Collections.emptyList());
    return roles.stream()
            .map(SimpleGrantedAuthority::new)
            .collect(Collectors.toList());
}
----

Wire the converter into the `SecurityFilterChain`:

[source,java]
----
.oauth2ResourceServer(oauth2 -> oauth2
    .jwt(jwt -> jwt.jwtAuthenticationConverter(keycloakJwtAuthenticationConverter())));
----

A complete working example is available in the `process-security` example delivered with the {PRODUCT_SHORT}, see xref:../05-getting-started/examples.adoc[Example Business Service projects].

[#mgmt-console-oidc-proxy]
== Connecting {MANAGEMENT_CONSOLE} to live _Business Services_
For {MANAGEMENT_CONSOLE} to authenticate and connect to a _Business Service_ that is secured through an Identity Provider, the instance must make the Identity Provider URL available. Different solutions exist for Quarkus and Spring Boot.

=== Quarkus

You need to use the `io.quarkiverse.oidc-proxy:quarkus-oidc-proxy` add-on, as it creates new endpoints in the _Business Service_ where one of them is `/q/oidc/.well-known/openid-configuration`, which provides the Identity Provider URL. It is the same URL that is defined in the `quarkus.oidc.auth-server-url` property.

To use the `io.quarkiverse.oidc-proxy:quarkus-oidc-proxy` add-on, add an entry with version `0.2.2` to the `<dependencies>` section of your POM file.

////
[source,xml]
----
<dependency>
  <groupId>io.quarkiverse.oidc-proxy</groupId>
  <artifactId>quarkus-oidc-proxy</artifactId>
  <version>0.2.2</version>
</dependency>
----
////
NOTE: Version 0.2.2 of `io.quarkiverse.oidc-proxy:quarkus-oidc-proxy` is compatible with Quarkus 3.20 (LTS). Do not use versions 0.1.x or 0.3.x.

=== Spring Boot

The `com.ibm.bamoe:bamoe-spring-boot-idp-discovery` add-on enables you to create an `/q/oidc/.well-known/openid-configuration` endpoint. It provides the Identity Provider URL which is the same URL that is defined in the `spring.security.oauth2.resourceserver.jwt.issuer-uri` property.

To use the `com.ibm.bamoe:bamoe-spring-boot-idp-discovery` add-on, add an entry to the `<dependencies>` section of your POM file.

////
[source,xml]
----
<dependency>
  <groupId>com.ibm.bamoe</groupId>
  <artifactId>bamoe-spring-boot-idp-discovery</artifactId>
</dependency>
----
////

Then add the endpoint as an exception to your web security configuration, for example:

[source,java]
----
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;

@Configuration
@EnableWebSecurity
@ConditionalOnProperty(name = "spring.security.oauth2.resourceserver.jwt.issuer-uri")
class BamoeSpringBootWebSecurityConfig {

    @Bean
    public SecurityFilterChain configure(HttpSecurity http) throws Exception {
        http
            .cors(cors -> {
            }) // enables CORS with default settings
            .csrf(csrf -> csrf.disable()) // disable CSRF
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/q/oidc/.well-known/openid-configuration").permitAll()
                    .anyRequest().authenticated())
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(jwt -> {
            }));

        return http.build();
    }
}
----

The configuration is only loaded if the `spring.security.oauth2.resourceserver.jwt.issuer-uri` property is set, which means that this `WebSecurityConfig` is only used when Spring Boot is configured to use an Identity Provider.

The `/q/oidc/.well-known/openid-configuration` path is added as an exception to make sure that the {MANAGEMENT_CONSOLE} is able to access it when adding this application as a connected Business Service.

Finally, make sure that the `spring.autoconfigure.exclude` property is `unset`.

[#rbac-config]
== Configuring Role-based access control (RBAC) for _Business Services_ at runtime
You can further protect interactions with your _Business Services_ in production using a Role-based access control (RBAC) system that reuses role definitions that already exist in the OpenID Connect Identity provider that you are using (Keycloak, Auth0, Okta, or Azure AD). This system enables you to:

* Hide {MANAGEMENT_CONSOLE} pages or actions from users that do not have the right permissions.
* Protect the underlying _Business Service_ REST and GraphQL endpoints by role.

The capability is available via the following add-ons, available for Quarkus and Spring Boot, that are part of the BAMOE BOM and can be added to your _Business Services_:

{RBAC_ADDON_SHORT}:: Exposes user permissions to the Management Console via a `/me` endpoint, and optionally cross-checks permissions against the security of the _Business Service_ route. 

BAMOE RBAC Data-Index Add-on:: Enforces role-based access on the Data Index GraphQL endpoint (`/graphql`).

The four BAMOE workflow accelerator templates include these libraries as part of the project POM file as well as the full RBAC configuration block in the `application.properties` (see xref:../06-available-components/accelerators/intro-accelerators.adoc#project-output[Accelerators → Generated project structure]). Once you have applied the appropriate accelerator to your BPMN model you can implement RBAC by simply uncommenting the dependencies and the properties blocks and replacing the role names. 

RBAC is a layered security feature. The {RBAC_ADDON_SHORT} controls what the user sees in the UI. Whereas the {PRODUCT_SHORT} RBAC Data-Index Add-on and the framework's built-in route security control what the different users of the _Business Service_ can call on the backend. To get a fully secure setup, customers should configure both.

NOTE: Quarkus Dev UI and Spring Boot Web Console are development tools and are not intended for production use and therefore RBAC is not applicable to their usage. They do not call `/me` and instead they receive the full permission list all users have access to all features are available during development.

=== How it works

The following sections describe the different phases of the RBAC system once it is configured for you _Business Service_. 

*Phase 1 — Connection on adding a _Business Service_ to the Management Console*

* The user enters the Business Service URL in the Management Console. 
* The Management Console queries the Business Service's `/q/oidc/.well-known/openid-configuration` endpoint to discover which Identity Provider is configured. No IdP URL is entered manually — the _Business Service_ advertises it. The user is redirected to the IdP login page, signs in, and is redirected back. 
* The Management Console exchanges that code for an access token and id token via a back-channel call to the IdP's token endpoint. The access token carries the user's roles in its claims and is sent on every subsequent request to the _Business Service_.

*Phase 2 — Permission resolution on login and token refresh*

* The Management Console calls `GET /me` on the _Business Service_. 

* The {RBAC_ADDON_SHORT} reads the roles from the token, looks them up in `application.properties`, and returns the user's name, roles, and resolved permissions. 

* If the {RBAC_ADDON_SHORT} is not installed, the call returns `404` and the Management Console falls back to unrestricted access.

*Phase 3 — Enforcement on every user action*

* The Management Console uses the permissions from `GET /me` to show or hide navigation items, buttons, and pages.
* When the user takes an action, both layers enforce the decision independently: 
** the framework's route security checks the token against configured path policies (returning `200`, `401` or `403` for REST), 
** the RBAC Data-Index Add-on checks roles against the configured GraphQL operations (returning data, `errorType: FORBIDDEN` or a list filtered to the user's tasks for `UserTaskInstances` for GraphQL). 
* The UI layer and the backend layer agree because both are driven by the same role-to-permission mappings in `application.properties`.

[#rbac-console-ops]
=== Controlling access to Management Console operations 
To limit access to your _Business Service_ functionality in Management Console, ensure your  _Business Service_ has the required {RBAC_ADDON_SHORT} dependency:

* On Quarkus: `com.ibm.bamoe:bamoe-addons-quarkus-rbac`

* On Spring Boot: `com.ibm.bamoe:bamoe-addons-spring-boot-rbac`

Both artifacts are part of the BAMOE BOM, so no explicit version is needed.

Your OIDC roles must be mapped to {PRODUCT_SHORT} permissions (see xref:#rbac-permissions[RBAC Permissions]) using the _Business Service_ `application.properties` file as shown below:

[source, properties]
----
bamoe.rbac.permissions.<role>=<permission1>,<permission2>,...
----

When your _Business Service_ is deployed the add-on auto-registers and exposes `GET /me` and optionally validates that permissions are aligned with the Business Service's REST route security. After OIDC login, the {MANAGEMENT_CONSOLE} uses the response that contains the user name, role(s) and the union of permissions across the role(s), to drive its UI response, as shown in the following example:

[source, json]
----
{
  "user": "alice",
  "roles": ["managers"],
  "permissions": [
    "process-definitions:view",
    "process-definitions:execute",
    "process-instances:view",
    "process-instances:update",
    "tasks:impersonate"
  ]
}
----

A role has no permissions until you configure them. The RBAC Data Audit Add-on layer works the same way, so the two layers agree by default (see xref:##graphql-rbac[Controlling GraphQL operations by role]). 

==== Console behavior with RBAC

The Overview page is always available to any authenticated user. The following list shows the expected behavior depending on the permissions configured for your Business Service:

* Navigation to specific pages from the left side bar is available or not depending on the `*:view` permissions.
* An Access Denied page if the user navigates directly to a restricted URL.
* Action buttons are hidden or deactivated depending on the `*:execute` or `*:update` permissions the user has, for example to abort, retry, complete, etc.
* The Impersonation section on task forms is hidden when the user does not have `tasks:impersonate` permission.

The following table describes different situations that may occur with RBAC configuration and the {MANAGEMENT_CONSOLE}:

[%header,cols=2]
[%autowidth]
|===
| Situation
| Behavior    

| Add-on present, permissions configured for the user's role                      
| Navigation, pages, and actions are filtered to match the user's permissions. Direct URL access to a restricted page shows the Access Denied page. 

| Add-on present, but no `bamoe.rbac.permissions.*` configured
| `/me` returns `permissions: []`. The Management Console treats RBAC as active and grants nothing. All sections except Overview are hidden. This is a misconfiguration.

| Add-on present, but permission name is incorrect, or an empty role name (for example `bamoe.rbac.permissions.=...`) 
| A warning is logged at startup and the permission is silently skipped. This is a misconfiguration.

| Add-on is not present (`/me` returns 404)
| The Management Console falls back to unrestricted access. All pages are visible, same behavior as before the capability.  

| `/me` returns a non-404 error (401, 403, 500) during login 
| Login fails with an error message.  

| `/me` errors during a token refresh 
| The error is swallowed, the existing permissions are kept, and a warning is logged. The user is not interrupted.
|===

==== Using the "All Business Services" view

When the Management Console connects to multiple Business Services in the All Business Services view:

. The Management Console queries `/me` on each connected runtime.
. What the user sees in this view depends on the union of permissions across all connected services where the add-on is present.
. Services without the add-on contribute nothing to the union.
. In mixed listings, rows from a _Business Service_ where the user lacks a permission are filtered out.
. If every _Business Service_ returns empty or undefined permissions, RBAC is treated as inactive in the All Runtimes view and behavior falls back to unrestricted access.

[#impersonation]
==== Impersonation

The `tasks:impersonate` permission enables a user to act on a User Task on behalf of another user. In order for this to work the User Task API endpoints must be configured for authentication using the `kogito.security.auth.enabled=true` and the role must be listed both in the `kogito.security.auth.impersonation.allowed-for-roles` property (see xref:##authentication-usertask-api[Authentication in User Task API endpoints]) and in the {RBAC_ADDON_SHORT} permission map:

[source,properties]
----
kogito.security.auth.enabled=true
kogito.security.auth.impersonation.allowed-for-roles=managers
bamoe.rbac.permissions.managers=tasks:impersonate,...
----

When startup validation is enabled (see xref:#startup-validation[Startup validation]), the add-on cross-checks these two properties; if `tasks:impersonate` is granted to a role that is not in `kogito.security.auth.impersonation.allowed-for-roles`, the add-on filters the permission out of the `/me` response.

[#startup-validation]
==== Startup validation

When `bamoe.rbac.validation.enabled` is set to `true`, the add-on validates the RBAC configuration at startup and on every `Get /me` request. This is to prevent the UI from advertising a permission that the backend does not actually enforce.

===== On Quarkus

Quarkus exposes route security through declarative `quarkus.http.auth.policy.*` and `quarkus.http.auth.permission.*` properties, which the {RBAC_ADDON_SHORT} can introspect. With validation enabled, the add-on checks each granted permission against:

. The static routes used by the {MANAGEMENT_CONSOLE}, for example:
** `pim:view` requires `GET /pim/plans` and `GET /pim/plan/*` to be secured for the user's role.
** `pim:update` requires `POST /pim/migration`, `POST /pim/plan`, and `DELETE /pim/plan/*` to be secured for the user's role.
** The `/svg/processes/*` route is associated with `pim:update`, `process-definitions:execute`, and `process-instances:view`.

. The Auto-generated BPMN routes. At startup, the add-on enumerates all Process IDs registered on the _Business Service_ and validates the implicit routes:
** `POST /{processId}` and `GET /{processId}/schema` &rarr; require `process-definitions:execute` coverage.
** `GET /{processId}/{instanceId}` &rarr; requires `process-instances:view` coverage.
** `DELETE /{processId}/{instanceId}` &rarr; requires `process-instances:update` coverage.
** `GET /{processId}/{instanceId}/{taskName}/{taskId}/schema` &rarr; requires `tasks:view` coverage.

. Impersonation, as described in xref:#impersonation[Impersonation].

Any permission whose corresponding route is not actually protected for the user's role is filtered out of the `GET /me` response, and a warning is logged. The user is not blocked from logging in, but will not see the affected UI elements. User Task transitions are not validated by this mechanism, since the User Task subsystem performs its own role-based authorization (see xref:##authentication-usertask-api[Authentification in User Task API endpoints]).

===== On Spring Boot

Spring Boot defines route security programmatically in a `SecurityFilterChain` bean, which cannot be introspected at runtime. As a result, when `bamoe.rbac.validation.enabled` is set to `true`, only impersonation is validated and the {RBAC_ADDON_SHORT} logs a message at startup explaining this limitation.

To verify alignment, configure the following:

. Extract roles from the JWT using a `JwtAuthenticationConverter`. For Keycloak, this means reading the `realm_access.roles` claim.
. Set the claim that holds the user name using `setPrincipalClaimName`. Keycloak populates the `sub` claim with a UUID; the human-readable login name is in `preferred_username`. For other providers (Auth0, Okta, or Azure AD), use the claim that carries the login name.
. Add `authorizeHttpRequests()` rules to restrict routes by role.
. Connect the converter to `oauth2ResourceServer().jwt(...)`.

[source,java]
----
@Bean
public JwtAuthenticationConverter keycloakJwtAuthenticationConverter() {
    JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(BamoeWebSecurityConfig::extractRealmRoles);
    converter.setPrincipalClaimName("preferred_username");
    return converter;
}
----

`setJwtGrantedAuthoritiesConverter` delegates role extraction to `extractRealmRoles`. For other providers (Auth0, Okta, or Azure AD), replace that method with one that reads the claim path your provider uses.

`setPrincipalClaimName` sets the JWT claim used as the principal name. If your token already carries the login name in `sub`, this line can be omitted.

Each setting has a distinct failure mode: without the roles converter, `/me` reports no permissions and every route guarded by `hasAuthority` answers 403; without the principal claim, permissions are correct but the user name remains a UUID, causing task-owner comparisons to fail.

[source,java]
----
private static Collection<GrantedAuthority> extractRealmRoles(Jwt jwt) {
    Map<String, Object> realmAccess = jwt.getClaim("realm_access");
    if (realmAccess == null) {
        return Collections.emptyList();
    }
    List<String> roles = (List<String>) realmAccess.getOrDefault("roles", Collections.emptyList());
    return roles.stream().map(SimpleGrantedAuthority::new).collect(Collectors.toList());
}
----

`extractRealmRoles` reads `realm_access.roles` from the token. If the claim is absent, it returns an empty list rather than throwing an exception. Each role is mapped to a `SimpleGrantedAuthority`, which is what `hasAuthority()` and `hasAnyAuthority()` rules evaluate.

The {PRODUCT_SHORT} Spring Boot accelerator templates include a `BamoeSpringBootWebSecurityConfig` class with an `extractRealmRoles` helper for Keycloak that you can adapt. The pattern follows the official Spring Security 6.5 guidance:

* https://docs.spring.io/spring-security/reference/6.5/servlet/oauth2/resource-server/jwt.html[Spring Security 6.5 - OAuth 2.0 Resource Server JWT] — wiring a custom `JwtAuthenticationConverter` into `oauth2ResourceServer().jwt(...)`.
* https://docs.spring.io/spring-security/reference/servlet/authorization/authorize-http-requests.html[Spring Security - Authorize HttpServletRequests] — `authorizeHttpRequests()` rules using `hasAuthority` / `hasAnyAuthority`.
* https://docs.spring.io/spring-boot/reference/web/spring-security.html[Spring Boot 3.5 - Spring Security] — the `spring.security.oauth2.resourceserver.jwt.issuer-uri` property and associated Spring Boot auto-configuration.

[#graphql-rbac]
=== Controlling access to GraphQL operations
The Management Console (and any other GraphQL clients) talks to Data Index through the `/graphql` endpoint. By default, every authenticated user can run every GraphQL query and mutation. The {PRODUCT_SHORT} RBAC Data-Index Add-on checks the role of a user before each operation.

You can use this add-on independently of the {RBAC_ADDON} to secure the GraphQL endpoints in your _Business Services_.

Add the following dependency in Quarkus:

`com.ibm.bamoe:bamoe-addons-quarkus-rbac-data-index`

Add the following dependency in Spring Boot:

`com.ibm.bamoe:bamoe-addons-spring-boot-rbac-data-index`

Each GraphQL operation is controlled individually using the syntax:

[source, properties]
----
bamoe.data-index.<OperationName>.roles=<role1>,<role2>,...
----

An operation with no `bamoe.data-index.<OperationName>.roles` property (or an empty value) is denied for all users, and stays denied until you list the roles allowed to call it which is the same behavior as `Get /me` layer. 

Only users whose roles are part of that list can call the operation. Everyone else receives a GraphQL error with `errorType: FORBIDDEN` and the following extensions:

[source, json]
----
{
  "extensions": {
    "code": "FORBIDDEN",
    "operation": "ProcessInstanceAbort",
    "requiredPermission": "process-instances:update"
  }
}
----

A feature can also depend on an operation controlled by a different permission. The Process Instance Migration (PIM) pages read Process Definitions through the `ProcessDefinitions` query, so a user with `pim:view` or `pim:update` also needs `process-definitions:view` to load them. 

// pim:view and pim:update are not available via GraphQL, should this be moved to Management Console?

=== Troubleshooting your RBAC configuration

The following table shows the common issues you may encounter when implementing Role-based access control for your _Business Services_.

[%header,cols=3]
[%autowidth]
|===
| Behavior
| Configuration
| Suggested solution 

| The user sees only the Overview page after login                 
| The add-on is present but `bamoe.rbac.permissions.<role>=...` is not configured for any of the user's roles
| Either add a permission mapping for one of the roles that include your user or remove the add-on dependency to fall back to unrestricted access

| A page is visible but actions are disabled even though the user is in the right group
| The Identity Provider may not be exposing the role in the JWT claim the framework reads
| In Spring Boot with Keycloak, roles reside in `realm_access.roles`, which Spring Security does not read by default. A `JwtAuthenticationConverter` is required (see https://docs.spring.io/spring-security/reference/6.5/servlet/oauth2/resource-server/jwt.html#oauth2resourceserver-jwt-authorization-extraction[Spring Security 6.5 - OAuth 2.0 Resource Server JWT: Extracting Authorities Manually documentation]

| Startup logs show `Permission '<x>' filtered out for user roles [...]`
| `bamoe.rbac.validation.enabled=true` is on and the add-on filtered the permission because the matching route is not secured for any of the user's roles
| Either add a `quarkus.http.auth.permission.*` policy for the route (Quarkus) or align the `SecurityFilterChain` rules (Spring Boot). On Spring Boot, route-level filtering is not performed automatically; only impersonation is validated

| GraphQL requests return `errorType: FORBIDDEN`
| The RBAC Data-Index Add-on is in use and the user's role is not in the `bamoe.data-index.<OperationName>.roles` list
| The error response includes the operation name and the BAMOE RBAC permission that controls it; use them to identify the missing role

| Tasks the user expects to see are missing from the Tasks page
| The Data-Index add-on filters `UserTaskInstances` per task assignment when the user does not have a role listed in `kogito.security.auth.impersonation.allowed-for-roles`
| To see all tasks, the user must be granted an impersonation role
|===

[#bus-services-tls-cert]
== Configuring _Business Services_ with Passthrough Transport Layer Security (TLS)
If you require end-to-end encryption between your user's browser and your _Business Service_ container you can use the required Accelerator and uncomment the TLS block properties in your `application.properties` file. No other dependencies or code changes are required. 

For Quarkus based _Business Services_ uncomment the following properties:

[source, properties]
----
%prod.quarkus.http.ssl.certificate.files=/var/run/secrets/tls/tls.crt
%prod.quarkus.http.ssl.certificate.key-files=/var/run/secrets/tls/tls.key
%prod.quarkus.http.insecure-requests=disabled
%prod.quarkus.http.http2=false
----

For Spring Boot based _Business Services_ uncomment the following properties:

[source, properties]
----
server.ssl.certificate=/var/run/secrets/tls/tls.crt
server.ssl.certificate-private-key=/var/run/secrets/tls/tls.key
server.http2.enabled=false
----

For _Business Services_ containing Workflows, you will need to force HTTPS-only, by switching `kogito.service.url`, `kogito.jobs-service.url`, and `kogito.data-index.url` to `https://`. You will find an inline note regarding this in the accelerator file.
