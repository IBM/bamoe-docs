= Deploying _Business Services_
include::../_partials/attributes.adoc[]
include::../_styles/images.adoc[]

Once you have defined your preferred way of building your _Business Services_ projects into your executable type (i.e., as
Container images, Native Executable, or standard JARs) you are ready to define your deployment strategy.

NOTE: In all deployments of _Business Services_ you must ensure license compliance, using the license solution adapted to your deployment architecture, see xref:../03-installing/licenses-and-tracking-usage/managing-license-entitlements.adoc[Installing → Licenses and tracking usage → Managing your license entitlements]

Follow industry-standard software development practices to version your _Business Services_ projects on Version Control Systems (VCS), and to automate the deployment process of your _Business Services_ using widely adopted services and tools.

While {PRODUCT_SHORT} does not dictate how you deploy your _Business Services_ to your production environment, there are a few important considerations to be taken into account, in particular if you are using stateful Workflows.

[#production-database-creation]
== Creating your database schema for stateful Workflows using {DDLS}

To initialize your application database, {PRODUCT_SHORT} provides a set of DDL (Data Definition Language) scripts in the bamoe-\{VERSION}-db-utils.zip deliverable that can be manually applied by a database administrator.

The Installation DDL scripts (contained in the `ddl` directory) enable you to create the database for the different {PRODUCT_SHORT} subsystems for your chosen database: PostgreSQL, Microsoft SQL Server, Oracle or Db2.

The scripts can be executed in any order. The required subsystem tables will be created in the database and used by the {PRODUCT_SHORT} Workflow engine.

It is also possible to use KIE Flyway to automatically add the Database tables at the first project execution. However this option is not recommended in your Production environment so before deploying your _Business Service_ containing stateful Workflows subsystems, you should disable KIE Flyway by setting the following property: 

[source,properties]
----
kie.flyway.enabled=false
----

[NOTE]
====
If you are using Microsoft SQL Server with a case-sensitive collation, some flyway migration scripts use different table name casing, which may cause failures on case-sensitive collations. You must set `kie.flyway.enabled=false` and use the DDL scripts to create the database schema manually.
====

[#evolving-deployed-workflows]
== Evolving stateful Workflows across _Business Service_ deployments

When deployed _Business Services_ with workflows are used to create Process Instances and you subsequently make changes to the project or the BPMN files and re-deploy, there are a few things to be considered.

You can directly deploy a new version of your application if there are no changes to Workflow models (BPMN files) or if your BPMN files are Straight-Through Processes (STPs) and the next Process Instances that are created by your system will be created with the new BPMN. 

If the Sequence Flow of a stateful Workflow BPMN model changes with new nodes, and/or new “paths” of execution, you cannot just update your BPMN file(s) in-place and deploy a new version of your application. You must consider how you want to manage long running Process Instances that may be in a wait state. The recommended strategy to manage the evolution of the Process Definitions in your project is to update your Business Service making the necessary modifications to the Process Definition and create a new Business Service version. The end result is a Business Service that corresponds to each Process Definition update. For more information on how to manage the evolution of a _Business Service_ containing workflows in a Runtime system see xref:#cross-bs-migration[Using Cross Business Service migration to evolve Workflow] 

[#cross-bs-migration]
=== Using Cross Business Services to evolve Workflow
The recommended strategy for evolving Process Definitions for long-running processes is the following:

. Make required changes to the BPMN model in your _Business Service_.
. Increment the BPMN Version property in {CANVAS} or the attribute in your BPMN file.
. Update the GAV version of your _Business Service_ in the project POM.
. Include the {PIM_ADDON_SHORT} in your _Business Service_ if not already part of the dependencies. 
. Ensure the previous and new _Business Services_ are configured to use the same database connection, preferably with Data isolation enabled to avoid any confusion between instances created by the two different versions of the _Business Service_, see xref:../08-developing-stateful-workflows/database-considerations.adoc#data-isolation-shared-databases[Database considerations → Data isolation on shared databases].
. Deploy the new _Business Service_ version. 
. Use PIM migration plans to migrate any Process Instances in a wait state to the Process Definition in the new version of the _Business Service_.
+ 
The PIM migration plan will have been created and tested prior to this step on a staging system and can be run manually or via the Automatic migration on startup, see xref:../10-managing-and-monitoring-business-services/migration-with-pim.adoc[Migrating Process Instances using {PIM_ADDON_SHORT}]

After deployment and before migration the old and new Business Service project structure would resemble this:

**Business Service v1 (still running, holding live instances):**

[source,xml]
----
my-business-service/
├── pom.xml                         # GAV -> org.example:my-business-service:1.0
└── src/
    └── main/
        └── resources/
            └── hiring.bpmn         # Process ID: "hiring", Version: "1.0"
----

**Business Service v2 (new deployment with the updated process):**

[source,xml]
----
my-business-service/
├── pom.xml                         # GAV -> org.example:my-business-service:2.0
└── src/
    └── main/
        └── resources/
            └── hiring.bpmn         # Process ID: "hiring", Version: "2.0"
----

=== Managing workflow evolution within the same Business Service
 Process Definitions in the same Business Service, duplicating them under a new name (and with a different ID), so that new Process Instances can be created based on the new version, while old Process Instances can continue their original Sequence Flow. Certain Workflows may be active for a long period so you can use the {PIM_ADDON} to map the source BPMN to the target BPMN for nodes in a waiting state, see xref:../10-managing-and-monitoring-business-services/migration-with-pim.adoc[Managing and Monitoring _Business Services_ →  Migration Process Instances using PIM].

////
The pseudo-timeline below shows the safest strategy for evolving your Workflow models across many deployments.

|===
| Action | Deployed processes | Note

| First deploy (v1)
| MyProcess.bpmn (added)
| Used for new Process Instances

| Second deploy (v2)
| MyProcess.bpmn (kept)
| Deprecate and do not allow creation of new Process Instances from it

|
| MyProcessV2.bpmn (added)
| Used for new Process Instances

| Third deploy (v3)
| MyProcess.bpmn (deleted)
| When there are no remaing active Process Instances that use this definition

|
| MyProcessV2.bpmn (kept)
| Used for new Process Instances
|===

There is no limit for how many different "versions" of a Workflow you can deploy in the same application. It may take some time for all Process Instances of an old version to be completed, and you can keep evolving your Workflow models by following this strategy.
////

[#multi-pod]
== Implementing multi-Pod Business Services containing stateful Workflows with a single database

When running multiple instances of _Business Services_ containing Workflows, on multiple Pods in the Compact Architecture, make sure you use the embedded Jobs Service add-ons, `org.kie:kogito-addons-quarkus-embedded-jobs` and `org.kie:kogito-addons-quarkus-embedded-jobs-jpa`, available from {PRODUCT_SHORT} {VERSION_930}. For the dependencies, see xref:../12-reference/maven-repository-libraries.adoc#_workflows_stateful_subsystem_jobs_service[Workflows (Stateful) subsystem → Jobs Service].

These add-ons are capable of running in a multi-pod setup without further configuration settings. The add-ons run a periodic task to synchronize the jobs loaded in-memory from the persistent store. If not specified, the interval is 10 minutes, which can be configured using the following property:

[source,properties]
----
kogito.jobs-service.schedulerChunkInMinutes=10
----

If a pod terminates unexpectedly, other pods will run any jobs created by this instance once the job data has been synchronized from the persistent store.

[NOTE]
====
If you use the embedded Jobs Service there is no need for further configuration. However if you have not yet upgraded your {VERSION_92X} Jobs Service to use the embedded Jobs Service, you will need to set the following configuration option.

`kogito.jobs-service.management.heartbeat.management-id=<id_string>`
====
