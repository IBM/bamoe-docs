= Upgrading from 9.5.x
include::../_partials/attributes.adoc[]
include::../_styles/images.adoc[]

This section describes the steps you must take to upgrade your {PRODUCT_SHORT} installation and _Business Services_ projects developed in version {VERSION_95x}.

See the following sections if you are upgrading from a version prior to this:

* xref:index.adoc[Upgrading from a previous version of {PRODUCT_SHORT}]

This guide walks you through upgrading your:

* {PRODUCT_SHORT} Dev environment with {MVN_REPO}, {CANVAS}, and {DEV_TOOLS}

* _Business Service(s)_ project(s)

* {PRODUCT_SHORT} Runtime environment with {MANAGEMENT_CONSOLE}, {MCP_SERVER} and upgraded versions of your _Business Services_

== Step 1: Download product archives

Start by downloading the product archives from {PRODUCT_PASSPORT_ADVANTAGE_LINK}[IBM Passport Advantage], or via the {DEV_PROGRAM_PAGE_LINK}[IBM Business Automation Manager Open Editions Developer Program]. 

== Step 2: Upgrade your {PRODUCT_SHORT} Dev environment

To upgrade your {PRODUCT_SHORT} Dev environment to {VERSION}, you can use the Dev environment Helm chart to install the updated component containers you require. The Dev helm chart includes the following component containers:

* {CANVAS}
* {EXT_SERVICES}
* {CORS_PROXY}
* {MVN_REPO}

=== Upgrade {CANVAS} and {MVN_REPO}
Use the https://docs.openshift.com/container-platform/4.19/applications/deployments/route-based-deployment-strategies.html#deployments-blue-green_route-based-deployment-strategies[blue-green deployment strategy] for Maven artifacts to be available for both your current version and {PRODUCT_SHORT} version {VERSION_94X}.

Follow the steps in xref:../03-installing/development-environment.adoc[Installing → Dev Environment Helm chart] to install the new {MVN_REPO} and {CANVAS} versions.

If you decide to uninstall the previous individual containers and replace with the Dev environment Helm chart, the {VERSION} version of {CANVAS} is a drop-in replacement for the {VERSION_95X} version. The projects you saved to your browser before the upgrade can simply be opened after installing the new version. 

You can import projects into the newly installed version (see xref:../06-available-components/dev-environment/bamoe-canvas/importing-existing-projects.adoc[{CANVAS} → Importing existing projects]) as long as the DNS domains between installations are different. If the DNS domains between installations are the same, your imported projects automatically show up in the new installation when you open it in your browser.

[NOTE]
====
If you have customized your previous {CANVAS} installation, remember to apply the same environment variables to the new installation. The same applies for customized container images for {CANVAS} Dev Deployments.
====

=== Upgrade {DEV_TOOLS}
{DEV_TOOLS} versions are managed by the Extension update mechanism in VS Code. You can set automatic updates or manage them manually when notified. Due to version differences in the models supported by the BPMN, DMN, and Test Scenario editors, plan your upgrade carefully to avoid issues when running models in services that have not yet been upgraded. See xref:../06-available-components/dev-environment/bamoe-developer-tools-for-vscode/index.adoc[{DEV_TOOLS}].

== Step 3: Upgrade your _Business Service(s)_ project(s)

_Business Service(s)_ project(s) can be upgraded by changing their Maven dependencies and configuration files.

The following tools are required to upgrade your _Business Service_ projects to {PRODUCT_SHORT} version {VERSION}:

- https://openjdk.org[JDK 21] is installed.
- https://maven.apache.org[Apache Maven latest version] is installed.
- https://code.visualstudio.com/download[Visual Studio Code IDE] latest version installed.
- Upgraded {PRODUCT_SHORT} Dev environment with {MVN_REPO} @ {IMAGE_VERSION}

Once your {PRODUCT_SHORT} Dev environment is upgraded, upgrading your _Business Service_ projects from {PRODUCT_SHORT} {VERSION_94X} to {PRODUCT_SHORT} version {VERSION} requires only minimal changes.

The project structure is not changed, and updates only need to be made to the versions and the names of some dependencies and files. 

Due to the update to Quarkus {QUARKUS_VERSION}, there are some changes which may impact your _Business Services_ built with {VERSION}. For more information, see xref:##quarkus-333-breaking[Breaking Quarkus Framework changes]. 

== Step 4: Verify the upgrade of your _Business Service(s)_ project(s)

To verify that your upgrade is successful, rebuild the project using Maven's standard command or any other customized build command you might have in your project.

[source,console]
----
mvn clean package
----

If your upgrade was successful, Maven prints `BUILD SUCCESS` at the end of the output.

You can now continue developing your _Business Service_ project on {PRODUCT_SHORT} version {VERSION}.

== Step 5: Upgrade your {PRODUCT_SHORT} Runtime environment

After upgrading your _Business Services_ source code (Step 3), upgrade the components in your Runtime environment.

The {MANAGEMENT_CONSOLE} and {MCP_SERVER} component containers are available in the Runtime Helm charts for your selected offering (DMOE or PMOE), including the product specific licensing annotations.

Install new versions of {MANAGEMENT_CONSOLE} and {MCP_SERVER}, by following the steps in xref:../03-installing/runtime-environment.adoc[Installing → Runtime Environment].

If you have stateful workflows in your _Business Services_, complete Step 6 to update your database. If you only have DMN and DRL in your _Business Services_, you can now deploy your upgraded _Business Services_.

[#migrate-stateful-workflow-db]
== Step 6: Upgrade your stateful Workflow database(s)

If you have _Business Services_ that run stateful workflows, upgrade your runtime database using the database migration scripts included in the `bamoe-{VERSION}-db-utils.zip` archive.

The archive provides scripts named `from--$PREVIOUS_RELEASE--to--$CURRENT_RELEASE.sql` for each subsystem in a _Business Service_ that uses the Compact Architecture (Data-Index, Data-Audit, Embedded Jobs Service, User Tasks, and Runtime Persistence).

You must upgrade your _Business Services_ and your databases together.

To upgrade safely:

. Back up your database

. Test the migration in a staging environment

. Schedule downtime if you are updating a production database

. Apply the scripts sequentially for each subsystem 

. Verify that all services function correctly after the upgrade

Avoid using KIE Flyway for automatic database schema migration in production environments. Instead, apply the scripts manually to maintain control and reduce the risk of issues.

When updating your stateful Workflow databases to {PRODUCT_SHORT} {VERSION_RM}, be aware of the following database schema and runtime behavioral changes:

Schema additions::
The {VERSION_RM} database migration scripts introduce new process identification and version columns to support data isolation between _Business Services_ sharing a database. The migration is backward compatible.

Permissive filtering for pre-upgrade data::
When data isolation (`kogito.persistence.data-isolation.enabled=true`) is enabled, pre-upgrade rows without the new column values populated are returned across all services permissively. This condition resolves as active process instances update or complete.

Fresh deployment recommendation::
For immediate, strict data isolation boundaries from initial launch, deploying to a fresh database is recommended over an in-place migration of active shared databases.

Data Events payload updates::
Data Events emitted by the Workflow Engine now include `processId`, `processVersion`, `rootProcessId`, and `rootProcessVersion` fields across all event types. Update downstream consumers expecting previous event payload formats accordingly.

For more information, see xref:../09-building-and-deploying-business-services/services-deployment.adoc#production-database-creation[Creating your database schema for stateful Workflows based on BAMOE Installation DDL scripts] and xref:../08-developing-stateful-workflows/overview.adoc[Overview of stateful Workflows with Compact Architecture].

Once you have installed your Runtime environment and updated the database for any stateful workflows, follow the standard guidance on how to deploy upgraded versions of your _Business Services_ (see xref:../09-building-and-deploying-business-services/services-build.adoc[Building Business Services executables] and xref:../09-building-and-deploying-business-services/services-deployment.adoc[Deploying Business Services]).

[#quarkus-333-breaking]
== Breaking changes due to Quarkus framework updates

The Quarkus version changed is part of the the {PRODUCT_SHORT} BOM. The changes and the actions you may need to take are described in the table below:

[%header,cols=2]
[%autowidth]
|===
|Change description
|Action

|The CORS configuration key has changed from `quarkus.http.cors` to `quarkus.http.cors.enabled`, including profile specific configuration.
|Search projects for `quarkus.http.cors=`, update every occurrence, including profile-specific configurations.

|Quarkus test artifacts are renamed*: from `*-junit5` to `*-junit`, due to change in underlying test framework has moved 
|No action, handled by Quarkus migration tooling.

|`@Specializes` is no longer accepted on a CDI bean and will cause the build to fail.
|If a custom user task assignment strategy extends `BasicUserTaskAssignmentStrategy` and is annotated `@Specializes`, remove the annotation and its import.

|The `quarkus-maven-plugin` requires `<extensions>true</extensions>` when the plugin is declared explicitly.
|If the application declares the Quarkus Maven plugin explicitly, make sure it contains `<extensions>true</extensions>`.

|The OIDC proxy Quarkiverse extension needs a compatible version.
|Update the OIDC proxy extension version to a compatible version, which may not be the newest available version.

|Multi-module Maven projects may need explicit dev-mode configuration
|For multi-module Maven applications that use `quarkus:dev`, add the `quarkus.bootstrap.workspace-discovery=false` property to the `application.properties` of each runnable module.
|===

This upgrade does not require any changes to {PRODUCT_SHORT} API coordinates, artifact coordinates, or BPMN, DMN, or DRL asset formats.

For Gradle projects, update the Quarkus test dependency:

[source,properties]
----
// before
testImplementation 'io.quarkus:quarkus-junit5'
// after
testImplementation 'io.quarkus:quarkus-junit'
----

Update `gradle.properties` as follows:

[source,properties]
----
# before
quarkusPlatformVersion=3.27.5.1
quarkusPluginVersion=3.27.5.1
quarkusOidcProxyVersion=0.3.2
# after

quarkusPlatformVersion=3.33.3.2
quarkusPluginVersion=3.33.3.2
quarkusOidcProxyVersion=0.5.0
----

`quarkusOidcProxyVersion` applies only to Gradle projects that use the OIDC proxy extension.
