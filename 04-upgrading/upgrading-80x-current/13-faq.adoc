== How do I migrate a {PRODUCT_SHORT} v8 KJAR to {PRODUCT_SHORT} v9?

{PRODUCT_SHORT} v9 no longer includes the KIE Server, so you cannot deploy a KJAR directly to a server as in v8.

The recommended approach to make your {PRODUCT_SHORT} v8 KJAR compatible with {PRODUCT_SHORT} v9 is to duplicate your {PRODUCT_SHORT} v8 project (to preserve a backup) and follow the steps outlined in the xref:05-00-upgrading-projects/index.adoc[Upgrading Projects] section.

== What is the deployment granularity for a Business Service?

In {PRODUCT_SHORT} v9, a _Business Service_ is a standalone, containerized application that encapsulates domain-specific logic, such as workflows, decisions, rules, or decision tables, and is built using Quarkus or Spring Boot. Each Business Service can be versioned, monitored, and managed independently, aligning with modern microservices best practices.

This represents a shift from {PRODUCT_SHORT} v8, where multiple business assets were typically bundled into a single KJAR and deployed to a centralized KIE Server.

With {PRODUCT_SHORT} v9, you define the granularity of your deployments. You have the flexibility to:

* Bundle multiple business assets (for example, BPMN, DMN, or DRL) into a single Business Service.
* Deploy multiple Business Services within the same Kubernetes pod for tighter coupling or resource efficiency.
* Separate Business Services into distinct deployments to improve modularity, scalability, and maintainability.

This flexibility allows you to tailor your deployment strategy to your organization's architecture, performance, and operational requirements. For additional information, see xref:../../09-building-and-deploying-business-services/index.adoc[Deploying Business Services].

== What are the alternatives to SmartRouter?

Since SmartRouter is no longer available in {PRODUCT_SHORT} v9, you can achieve similar load balancing using any solution compatible with cloud environments.

== What are the alternatives to the {PRODUCT_SHORT} v8 Operator?

{PRODUCT_SHORT} v9 does not provide its own Operator. Instead, it offers Helm charts to simplify deployment. The {PRODUCT_SHORT} dev and runtime Helm charts install all required components in your development or runtime environment on Kubernetes or OpenShift clusters. These charts support flexible configuration and align with infrastructure-as-code practices. For more details, see xref:../../03-installing/index.adoc[Installing].

== My {PRODUCT_SHORT} v8 BPMN uses `#{variable_name}` in a Call Activity and fails to build in {PRODUCT_SHORT} v9 with an _illegal '#' character_ error

In {PRODUCT_SHORT} v9 prior to 9.6.0, using the `#{variable_name}` syntax in a Call Activity `calledElement` caused a build error: _illegal '#' character_. {PRODUCT_SHORT} v8 BPMN files that relied on dynamic sub-process calling could not be deployed on {PRODUCT_SHORT} v9.

From {PRODUCT_SHORT} 9.6.0 onwards, this syntax is fully supported. No changes to the BPMN file are required — deploy the existing BPMN as-is to {PRODUCT_SHORT} 9.6.0 or later and verify that all referenced sub-processes are included in the same deployment.

For more information, see xref:05-00-upgrading-projects/05-04-upgrading-individual-assets.adoc#dynamic-call-activity-migration[Upgrading individual assets → Dynamic Call Activity] and xref:../../08-developing-stateful-workflows/authoring-workflows.adoc#dynamic-call-activity[Authoring Workflows → Calling sub-processes dynamically].
