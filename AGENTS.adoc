= AI Agent Rules — IBM Business Automation Manager Open Editions (BAMOE) Documentation
:toc: left
:toc-title: Rules Index
:toclevels: 2

This file defines mandatory rules for AI agents (Codex, Copilot, Bob, or any other automated tool) that read, write, or modify content in this repository.
All rules are *binding*.
When in doubt, err on the side of caution: do less, ask a human reviewer, and never guess at product names, version numbers, or cross-reference targets.

== 1. Understand the Repository

=== 1.1 Purpose

This repository contains the official product documentation for {PRODUCT_LONG} ({PRODUCT_SHORT}).
It is a pure-documentation repository: there is no application source code to build or test.
The output is a set of HTML pages generated by Asciidoctor.

=== 1.2 Repository Layout

[cols="1,3",options="header"]
|===
| Path | Purpose

| `01-release-notes/` … `13-support-notices/`
| Numbered top-level content directories, each mapped to one section of the navigation.

| `_partials/attributes.adoc`
| Central attribute file.
All product names, version strings, and external URLs are defined here and *must not* be hard-coded elsewhere.

| `_images/`
| All image assets referenced by the documentation.
Never place images in a content directory; always reference from this root-level directory.

| `_styles/images.adoc`, `_styles/tabs.adoc`
| Shared passthrough CSS blocks.
Include them at the top of every content file that uses images or tabs.

| `_code/`
| Code samples used as live references in the documentation.
Do not delete or rename files here without updating every `include::` that references them.

| `nav.adoc`
| Table of contents file in Antora navigation format.
Every new `.adoc` page *must* have a corresponding entry here.

| `CONTRIBUTING.adoc`
| Human-authored contributor guide.
Do not overwrite or shorten it.
|===

== 2. File and Content Authoring Rules

=== 2.1 Document Header

Every content `.adoc` file *must* begin exactly as follows, with no blank lines between the three lines.

Files at the **root level** of the repository (e.g., `AGENTS.adoc`, `README.adoc`):

[source,asciidoc]
----
= <Page Title>
include::_partials/attributes.adoc[]
include::_styles/images.adoc[]
----

=== 2.2 One Sentence Per Line

Write exactly one sentence per line.
Do not wrap sentences across lines.
Do not place two sentences on the same line.
This rule applies to all prose, bullet points, table cells, admonition blocks, and list items.

=== 2.3 Use Defined Attributes for All Product Names and Versions

*Never* hard-code a product name, version number, or external URL.
Use only the attributes defined in `_partials/attributes.adoc`.

[source,asciidoc]
----
// Correct
{PRODUCT_SHORT} {VERSION_X} is now available.

// Wrong
BAMOE 9.6.x is now available.
----

Commonly used attributes:

* `{PRODUCT_SHORT}` → `BAMOE`
* `{PRODUCT}` → `IBM BAMOE`
* `{PRODUCT_LONG}` → `IBM Business Automation Manager Open Editions`
* `{VERSION_X}` → current version series (e.g., `9.6.x`)
* `{VERSION}` → exact current release (e.g., `9.6.0`)
* `{CANVAS}` → `BAMOE Canvas`
* `{DEV_TOOLS}` → `BAMOE Developer Tools for VS Code`

=== 2.4 Cross-References

Use `xref:` for all internal cross-references.
Never use bare relative paths in link text.

[source,asciidoc]
----
// Correct — relative from the current file's directory
xref:../03-installing/development-environment.adoc[Installing → Development Environment]

// Wrong — do not use raw URL or omit section label
link:03-installing/development-environment.html[dev env]
----

Provide descriptive link text in the format `Section → Subsection`.

=== 2.5 Images

* Store every image under `_images/`, in a subdirectory that reflects the content section.
* Reference images with a path relative to `_images/` using the `:imagesdir:` attribute already set in `_partials/attributes.adoc`.
* Use the `.Image title` caption convention before every `image::` macro.
* Every screenshot *must* have a drop-shadow applied before being committed (see `CONTRIBUTING.adoc` for the ImageMagick command).
* When highlighting parts of a screenshot, use only colour `#008CB4`.

[source,asciidoc]
----
.DMN Editor overview
image::tools/authoringDecisions/overview.png[DMN Editor overview]
----

=== 2.6 Code Blocks

Always specify the source language for every code block.

[source,asciidoc]
----
[source,java]
----
// Java code here
\----

[source,shell]
----
# Shell commands here
\----
----

Acceptable language identifiers include: `java`, `xml`, `yaml`, `json`, `shell`, `bash`, `asciidoc`, `properties`, `sql`, `javascript`, `typescript`.

=== 2.7 Tables

Place each column value on its own line.
Separate rows with a blank line.
Always include `options="header"` and `[cols="…"]` on every table.

[source,asciidoc]
----
[cols="1,3",options="header"]
|===
| Column A
| Column B

| Value 1
| Description 1

| Value 2
| Description 2
|===
----

=== 2.8 Admonition Blocks

Use the multi-line block form (`====`) for all admonitions, never the inline paragraph form.

[source,asciidoc]
----
[NOTE]
====
This is a note.
====

[WARNING]
====
This is a warning.
====
----

Admonition types and their intended use:

[cols="1,3",options="header"]
|===
| Type | When to use

| `NOTE`
| Additional context or helpful clarification.

| `TIP`
| Optional best practice or shortcut.

| `IMPORTANT`
| Information the reader must not skip.

| `WARNING`
| Risk of data loss, service interruption, or incorrect behaviour.

| `CAUTION`
| Action that is irreversible or has side-effects.
|===

=== 2.9 Grammar and Spelling

After writing or editing any prose in an `.adoc` file, perform the following checks before considering the change complete:

. *Spelling* — every word must be correctly spelled in American English.
Exceptions apply to: product names and component names defined in `_partials/attributes.adoc`, technical identifiers (class names, CLI flags, property keys), and terms inside source code blocks.

. *Grammar* — sentences must be grammatically correct, use active voice where possible, and avoid ambiguous pronoun references.

. *Terminology consistency* — use the same term throughout a page and across the documentation.
Do not mix synonyms for the same concept (e.g., do not alternate between "workflow" and "process" when referring to the same artifact).

. *Procedure language* — steps in numbered lists must begin with an imperative verb (e.g., "Click", "Open", "Run").

. *Avoid filler phrases* — do not use "simply", "just", "easy", "straightforward", "obviously", or similar qualifiers.

*Automated check*: if `vale` is installed locally, run the following command against every file you modified before committing:

[source,shell]
----
vale <path/to/modified-file.adoc>
----

Treat every `error` and `warning` reported by Vale as a blocker.
Treat `suggestion` level findings as informational; resolve them where practical.

=== 2.10 Tech Preview Content

Mark any feature flagged as Tech Preview with the following admonition immediately after the section heading:

[source,asciidoc]
----
[IMPORTANT]
====
This feature is a Technology Preview.
Technology Preview features are not supported for use in production environments.
====
----

== 3. Navigation File Rules

=== 3.1 Every New Page Requires a `nav.adoc` Entry

After creating a new `.adoc` file, add a corresponding `xref:` entry to `nav.adoc` in the correct position within the existing hierarchy.
The link text must match the page title exactly.

=== 3.2 Do Not Reorder Existing Entries

Do not change the order of existing entries in `nav.adoc` without explicit instruction from a human reviewer.

=== 3.3 Commented-Out Entries

Entries commented out with `//` are intentionally hidden.
Do not uncomment them without explicit human instruction.

== 4. Version and Branch Awareness

=== 4.1 Current Branch is `9.6.x`

All new content must target the `9.6.x` branch.
Do not backport changes to earlier version branches unless explicitly instructed.

=== 4.2 Version Attribute Updates

When a new micro-release is published, update *only* `_partials/attributes.adoc`.
Never update version strings in individual content files.

=== 4.3 Deprecated and EOL Content

Do not remove deprecated content without replacing it with a deprecation notice.
Do not recommend software components that are End of Life.

== 5. Prohibited Actions

The following actions are *strictly forbidden*:

* Hard-coding any product name, version number, or URL that is already defined in `_partials/attributes.adoc`.
* Deleting or renaming any image file in `_images/` without updating every reference to it.
* Deleting or renaming any file in `_code/` without updating every `include::` directive that references it.
* Removing or altering the `CONTRIBUTING.adoc` or `README.adoc` files.
* Creating a new `.adoc` file without adding a corresponding entry in `nav.adoc`.
* Wrapping multiple sentences on a single line.
* Using bare relative-path links instead of `xref:` macros for internal navigation.
* Placing images in content directories rather than in `_images/`.
* Committing screenshots that do not have a drop-shadow applied.
* Uncommenting hidden `nav.adoc` entries without explicit human instruction.
* Adding `<script>` tags or inline JavaScript to any file.

== 6. Pull Request and Commit Rules

=== 6.1 Branch Naming

All work must be done on a feature branch created from `9.6.x`.
Never commit directly to `9.6.x`, `main`, or any other protected branch.

=== 6.2 Commit Scope

Each commit should be limited to a single logical change (e.g., one section updated, one page added).
Do not bundle unrelated changes in one commit.

=== 6.3 Do Not Rebase Published Branches

Never rebase a branch that has already been pushed to the remote.
Merge the upstream branch into your feature branch instead.

=== 6.4 Pull Request Description

A pull request description must include:

* A one-sentence summary of the change.
* The section(s) of the documentation affected.
* A note on whether any `nav.adoc` entries were added or modified.

== 7. Validation Checklist Before Any Commit

Before committing, verify every item below:

* [ ] Every modified `.adoc` file starts with the correct three-line header (path depth-aware).
* [ ] No product name, version, or URL is hard-coded; all use attributes from `_partials/attributes.adoc`.
* [ ] Every `image::` reference points to an existing file under `_images/`.
* [ ] Every new page has a matching entry in `nav.adoc`.
* [ ] All cross-references use `xref:` with descriptive link text.
* [ ] All code blocks have an explicit source language.
* [ ] One sentence per line throughout.
* [ ] No deprecated or EOL packages, base images, or software referenced.
* [ ] The Asciidoctor build produces no new warnings (`asciidoctor -vw`).
* [ ] Spelling is correct in American English (excluding defined attributes and code blocks).
* [ ] Grammar is correct; active voice used; no filler phrases present.
* [ ] Terminology is consistent with the rest of the page and the surrounding section.
* [ ] `vale <file>` reports zero errors and zero warnings (if Vale is available).
