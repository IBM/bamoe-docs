Before you start using {PRODUCT_LONG}, review the known limitations. Workarounds are included with the limitations when possible.

Table 1. Known limitations
[%header,cols=4]
[%autowidth]

|Limitation |Description |Versions |Workaround

|BPMN Editor: Timer configuration resets when editing multiple Timer Events.
|When you configure two timer nodes in a BPMN file, the settings of the first timer node reset incorrectly after you navigate away and return to it. The editor resets the timer option to "Fire multiple times" and changes the syntax dropdown to ISO, even though the CRON value remains in the text field.
|{VERSION_950}
|After you configure the first timer node, click any other node before configuring the second timer node. This action prevents the reset and preserves the correct timer option and syntax selection.

|Native compilation support for workflow projects.
|Workflow (BPMN) projects do not support native compilation in {PRODUCT_SHORT} {VERSION_X} and earlier 9.x versions. Using certain dependencies (for example, data-index, jobs-service) might cause native builds to fail due to missing reflection metadata.
|{VERSION_950}
|Do not use native compilation if your _Business Services_ include stateful workflow.

|OpenAPI spec auto-generation when using the _io.quarkus:quarkus-oidc_ extension.
|The _io.quarkus:quarkus-smallrye-openapi_ extension will cause errors when starting a Business Service if the _io.quarkus:quarkus-oidc_ extension is also present and no other schema is generated. This only happens if the _io.quarkus:quarkus-oidc_ extension is enabled.
|{VERSION_950}
|Add the following to your `application.properties` file:
`quarkus.smallrye-openapi.auto-add-bad-request-response=false`

* This property ensures that "400 Bad Request" outputs are not added to the auto-generated OpenAPI specifications.

|DMN Editor: Does not support DMN 1.6 Simplified `InputData` Assignment Across Nested Imports
|Users who rely heavily on imported DMN models to build modular DMN models with layered imports, may encounter issues when their model depends on transitively imported Input Data nodes. This refers to Input Data defined in a model that is imported indirectly through another model. As a result, models using transitive Input Data cannot be:

* Evaluated using DMN Runner

* Tested using Scenario and Simulation files

|{VERSION_950}
|To avoid this issue, users must restructure their models to avoid relying on nested imports for Input Data.

| BAMOE Canvas: Misleading Dev Deployment status for Kind/Minikube deployments
| After creating a Dev Deployment targeting Kind or Minikube clusters, BAMOE Canvas fails to retrieve healthcheck data from the deployment and displays it in an error state, even if the deployment succeeded. Dev Deployments targeting OpenShift clusters work as expected.
|{VERSION_940} only
| It is still possible to access the deployment by manually typing the URL in the browser: `http://localhost/<dev_deployment_id>/q/swagger-ui` for Quarkus and `http://localhost/<dev_deployment_id>/swagger-ui/index.html` for Spring Boot. The error state can be ignored.


|Quarkus Dev UI / Spring Boot Web Console / Management Console: User Task forms fail to load when Business Service runs under a sub-path.
|User Task Forms fail to load in the Quarkus Dev UI, Spring Boot Web Console, and Management Console when the Business Service runs under a sub-path (configured via `quarkus.http.root-path` or `server.servlet.context-path`).
|{VERSION_940} only
|To avoid this issue, use one of the following alternatives:

* Create the Dev Deployment in an OpenShift cluster instead
* Test the Business Service locally instead of using Dev Deployments
* Submit or transition the User Task directly using the REST API

|Kafka consumer group ACL configuration requires review.
|BAMOE includes Apache Kafka components affected by CVE-2026-41115. This issue is caused by a discrepancy between the Kafka documentation and the actual authorization behavior of the CONSUMER_GROUP_DESCRIBE API. The Kafka implementation correctly requires the DESCRIBE permission on a GROUP resource, while the documentation previously indicated that READ permission was required. No software fix is available because the implementation is functioning as intended. However, existing Kafka ACL configurations may require review to ensure permissions are granted appropriately.
|{VERSION_950}
|Review Kafka consumer group ACLs and verify that permissions are configured according to the corrected authorization model. Grant DESCRIBE permissions only where required and remove unnecessary permissions to maintain the principle of least privilege.

|Workflow Engine: Extra tasks are generated after timer node execution in multi-instance subprocess
|Extra tasks are generated after timer node execution in multi-instance subprocess.
|{VERSION_950}
|Add the following to your `application.properties` file:
`kogito.jobs-service.numberOfWorkerThreads=1`
